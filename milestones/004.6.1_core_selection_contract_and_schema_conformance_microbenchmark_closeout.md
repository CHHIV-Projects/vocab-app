## 3. Corrected benchmark contracts and diagnostics

### 3.1 Current subset-array contract

The harness calls the actual `core_selection_schema()` helper, then applies benchmark-only decomposed diagnostics:

- `parse_success`;
- `exact_top_level_keys`;
- `core_group_ids_is_array`;
- `all_ids_are_strings`;
- `all_ids_in_allowed_set`;
- `ids_are_unique`;
- `count_within_limit`.

The corrected `subset_diagnostics(parsed, allowed_ids)` accepts the actual allowed-ID set per attempt. Phase A uses synthetic `G001...G006`; Phase C uses every fixture's own `allowed_group_ids`. It no longer relies on a hard-coded synthetic set when validating reconstructed fixtures.

### 3.2 Benchmark-only fixed-key contract

The isolated alternative requires:

```json
{
  "core_count": 3,
  "scores": {
    "G001": 5,
    "G002": 2,
    "G003": 4
  }
}
```

Every code-owned ID is a required `scores` property. `additionalProperties: false` is used at both object levels, each score is an integer 0–5, and `core_count` is an integer from 1 through `min(5, group_count)`.

The strict benchmark diagnostics separately check:

- exact top-level keys;
- valid `core_count`;
- `scores` object type;
- every expected score key present;
- no unknown score keys;
- every score's integer type/range;
- deterministic-assembly success.

Missing scores are never accepted as zero. Assembly is rejected unless all acceptance diagnostics pass. On accepted data, code sorts by descending score and then ascending code-owned group ID before taking `core_count`; therefore model output never owns final candidate identity, duplicate identity, cross-POS identity, or a final selection larger than five.

## 4. Qwen `done_reason: length` diagnosis and correction

The earlier partial run used the current production-shaped provider defaults for Qwen: `think: "low"` and `num_predict: 3200`. For small schema tasks, Qwen generated reasoning in `message.thinking` and exhausted the output budget before emitting final JSON. Raw earlier evidence included `done_reason: "length"`, `eval_count: 3200`, empty `message.content`, and nonempty reasoning. This was an invocation/budget effect, not evidence that Qwen could not satisfy the structured contract.

A direct, benchmark-local diagnostic established the safe correction:

| `qwen3:8b` invocation | Result |
|---|---|
| `think: "low"`, `num_predict: 256` | `done_reason: length`, 256 evaluation tokens, no final content, 1,188 reasoning characters |
| `think: false`, `num_predict: 256` | `done_reason: stop`, 30 evaluation tokens, final JSON present, no reasoning field content |

The completion benchmark therefore uses **only for Qwen benchmark calls**:

```json
{
  "think": false,
  "options": {
    "temperature": 0,
    "num_predict": 256,
    "num_ctx": 16384
  }
}
```

This is an explicit benchmark-local request setting passed to the existing Ollama API. It did not alter global Ollama configuration or the production `OllamaProvider`. The setting and output limit are retained in each Qwen artifact's identity. It is justified because the experiment is a bounded classification/ranking contract, while the prior setting demonstrably consumed the output budget in Qwen reasoning before JSON generation.

Raw failure classes are distinct in the harness: `transport_failure`, `timeout`, `done_reason_length`, `empty_content`, `json_parse_failure`, `provider_success`, and subsequent parsed predicate diagnostics. The completion run produced `provider_success` for every attempt; the earlier partial outputs remain evidence of the `done_reason_length` failure class and its diagnosed cause.

## 7. `uniqueItems` conclusion

The result must retain three separate layers:

1. **Documented runtime capability:** the deployed llama.cpp JSON-Schema path does not enforce `uniqueItems`; deterministic application validation remains mandatory.
2. **Observed GPT-OSS behavior:** no duplicate IDs appeared in five duplicate-directed standardized Phase A attempts.
3. **Observed Qwen behavior after the correction:** no duplicate IDs appeared in five duplicate-directed standardized Phase A attempts.
4. **Historical production evidence:** the raw `Utilitarian` provider output was not retained. The exact failing predicate cannot be reconstructed.

Thus, the duplicate hypothesis is **still unproven**. The new small sample weakens any claim that duplicates are frequent for either measured model under this prompt, but it cannot prove uniqueness enforcement or exclude a historical duplicate response.

## 8. Architectural conclusion and production recommendation

The measured evidence does not show a current failure of the subset-array contract for either model in the small reconstructed-fixture corpus: both completed all measured structurally constrained calls after Qwen's invocation was corrected.

The fixed-key contract is nevertheless structurally safer by construction for identity/topology concerns: candidate identities are code-owned required keys, key coverage is explicit, and code builds the selected set with a stable tie-breaker. It does not prove semantic superiority, and its extra response cost is modest rather than free.

Therefore:

> Do not change production core selection yet. Retain deterministic production validation. Treat contract design as the primary structural-safety lever, but require a later human-reviewed semantic comparison before adopting the fixed-key contract. The evidence does not support replacing `gpt-oss:20b` solely because of the historical failure, and it shows `qwen3:8b` is a credible faster challenger for this bounded task when reasoning is disabled locally.

The result favors testing a code-assembled bounded ranking contract over assuming model size alone will solve structural reliability. Multi-model routing remains unapproved architecture, and no runtime migration is justified.
