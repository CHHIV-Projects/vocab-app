## 3. Current synthesis pipeline

The current source implements this pipeline:

1. `vocab_lexical_engine.lookup()` performs exact normalized-lemma lookup against the immutable lexical SQLite dataset and retrieves WordNet evidence.
2. `project_synthesis_evidence()` creates a bounded canonical evidence package.
3. `evidence_set_hash()` creates the stable evidence/cache identity.
4. `SynthesisRuntime.read_cache()` returns an already validated whole synthesis envelope when available.
5. `sense_aliases()`, `scaffold_schema()`, `scaffold_prompt()`, and `validate_scaffold()` request one learner paraphrase for every code-owned source-sense alias.
6. `scaffold_to_content()` deterministically converts those paraphrases into provisional meaning records.
7. Grouping runs separately by POS and material-label partition. Code defines allowed aliases and group IDs; the model assigns aliases to IDs and writes group definitions.
8. `validate_grouping()` checks alias coverage, allowed group IDs, group-definition coverage, used-group definitions, and material-label boundaries.
9. Code remaps used partition-local groups into POS-local `G001...Gnnn` IDs.
10. Core selection asks the model for up to five IDs from that POS-local set.
11. `grouped_content()` deterministically divides core and Additional Meanings from the selected IDs and complete group coverage.
12. Synonym enrichment is deterministic and evidence-ID-bound.
13. Etymology enrichment uses canonical evidence with model-assisted summary language.
14. `validate_content()` deterministically verifies coverage, labels, examples, evidence references, and POS boundaries.
15. Only validated envelopes are written to the synthesis cache and can proceed through workflow/save versioning.

## 4. Authority boundary

| Stage | Code owns | Learned model owns | Acceptance control |
|---|---|---|---|
| Exact lookup | query, canonical records, WordNet retrieval | nothing | deterministic result |
| Evidence projection/hash | bounded evidence and identity | nothing | deterministic construction |
| Sense scaffold | aliases and required coverage | learner paraphrase text | schema plus `validate_scaffold()` |
| POS grouping | POS/material partitions, allowed aliases/IDs | bounded assignments and group-definition language | schema plus `validate_grouping()` |
| Core selection | candidate IDs and final validity checks | semantic subset choice | constrained output plus application predicate |
| Additional Meanings | complete deterministic partition from core selection | nothing | `validate_content()` |
| Synonyms | evidence-linked relations | nothing | deterministic evidence checks |
| Etymology | evidence and references | concise summary language | evidence-bound validation |
| Persistence | cache and accepted-version identity | nothing | deterministic validation and hashes |

The governing principle remains:

> AI decides bounded semantics; code owns identity, topology assembly, validation, and acceptance.

The current implementation already follows this principle in part. The remaining design question is how far grouping and core selection should be reduced from generative structures to bounded judgments.

## 6. Exact core-selection scope and failure analysis

### 6.1 Construction and scope of `global_ids`

The exact source path in `synthesize_word()` is:

1. scaffold results are accumulated in `per_pos`, keyed by POS;
2. grouping is performed separately for each POS and material-label partition;
3. each result is stored as `(pos, grouping, aliases, partition)`;
4. core selection runs inside `for pos in sorted(per_pos)`;
5. `partitions = [item for item in group_results if item[0] == pos]` selects only results for the current POS;
6. `global_definitions = {}` and `next_group = 1` are initialized inside that one-POS iteration;
7. used partition-local IDs are remapped into POS-local `G001...Gnnn` IDs;
8. `global_ids = sorted(global_definitions)` is created from that POS-local dictionary;
9. the prompt receives those IDs through its `groups` list;
10. `core_selection_schema(global_ids)` uses that same list as its item enum;
11. the application validator compares the parsed response directly with the unchanged `global_ids`.

Consequently:

- `global_ids` contains groups for one POS only;
- the schema enum and application validator use the same membership set;
- group labels may recur in another POS, but that other POS is handled by a separate request and local variable scope;
- no ordinary cross-POS narrowing occurs between schema generation and validation;
- no transformation, filtering, or mutation changes the valid set between the request and validator;
- sorting changes order only and cannot invalidate an otherwise valid member.

An ID cannot be enum-valid for that request and then be rejected because the validator applies a narrower POS-local membership rule.

### 6.2 Parsing and validation

The application does not run a separate general-purpose JSON Schema validator after the response. It performs:

1. constrained generation requested through Ollama's `format` field;
2. exact-object parsing through `strict_json_object()`;
3. a hand-written compound predicate.

The visible error:

```text
Model core selection was not a valid subset of POS groups
```

is emitted when any of the following is true:

- the object has the wrong keys;
- `core_group_ids` is not an array;
- the array contains duplicate IDs;
- an ID is outside `global_ids`;
- the array contains more than five IDs.

The message therefore does not prove that an out-of-set or cross-POS ID was returned.

### 6.3 Most defensible current conclusion

Ollama 0.32.5 uses its llama.cpp path to constrain supported schema features during decoding. `enum`, required properties, `additionalProperties: false`, and `maxItems` are supported. The deployed llama.cpp grammar path does not enforce `uniqueItems`.

Duplicate valid IDs are therefore the leading current hypothesis: they could be valid under runtime grammar constraints but fail the application's explicit uniqueness predicate.

That hypothesis is **not proven**. The original `Utilitarian` provider response was not retained, so the exact failed predicate remains unknown. A runtime regression or version-specific defect remains technically possible, but current source rules out ordinary cross-POS narrowing, stale stage state, cache mismatch, and post-schema membership mutation.

The incident establishes a diagnostics and contract-conformance gap, not a proven failure of enum enforcement or a proven need to replace the runtime.

## 7. Grouping and LLM necessity

Grouping remains the more substantial topology question:

- code defines aliases, POS/material-label partitions, and allowed group IDs;
- the model chooses assignments and supplies definitions;
- code rejects unknown groups, incomplete alias coverage, missing used-group definitions, and material-label boundary violations;
- the retained `runner` failure demonstrates a real grouping contract failure.

A safer candidate design is:

```text
code supplies bounded candidates
    -> learned component judges equivalence/ranking
    -> code constructs final groups and IDs
    -> generative model writes learner wording only where needed
    -> deterministic validator accepts or rejects
```

Generative language remains justified for learner paraphrases and evidence-grounded etymology summaries. Group equivalence and core ranking may be better served by bounded classification, ranking, or pairwise judgment. Exact lookup, evidence identity, Additional Meanings calculation, synonym mapping, topology assembly, and final validation should remain deterministic.

## 10. Quantitative embedding architecture

For approximately 1.9 million sense vectors, raw storage is:

| Dimensions | float32 | float16 |
|---|---:|---:|
| 384 | approximately 2.92 GB | approximately 1.46 GB |
| 768 | approximately 5.85 GB | approximately 2.92 GB |
| 1024 | approximately 7.79 GB | approximately 3.90 GB |

These are raw decimal storage estimates and exclude sense-ID mapping, manifests, alignment, metadata, and index overhead.

### 10.1 Exact-word grouping

```text
exact lexical lookup
    -> retrieve vectors only for returned senses
    -> ordinary in-memory pairwise similarity
    -> bounded semantic adjudication
```

An exact word normally yields tens or, in difficult cases, hundreds of candidate senses. Exact pairwise comparison is practical at that scale. ANN infrastructure is not required merely to support M004.6 grouping.

### 10.2 Future global semantic search

```text
query vector
    -> search approximately 1.9M sense vectors
    -> ANN candidate retrieval
    -> optional reranking
```

Global search may justify FAISS or an equivalent ANN index. A flat immutable matrix remains the simplest storage for exact sense-ID retrieval. PostgreSQL/pgvector is more natural for mutable application data than for the versioned immutable lexical corpus, while a SQLite vector extension would require a deliberate operational decision.

### 10.3 Dataset versioning and reuse

The artifact should record:

- canonical sense ID;
- deterministic projection text or projection hash;
- embedding model and artifact digest;
- tokenizer/model revision;
- projection, pooling, normalization, and numeric-storage policy;
- lexical dataset version;
- vector/index checksums.

Vectors may be reused across later Wiktionary builds only when the canonical sense content/projection and all embedding-policy identities are unchanged.

Embeddings are semantic screening and ranking evidence. They are not lexical truth and must not own final topology.

## 11. SQLite exact-retrieval finding

This is a separate lexical-performance issue, not a cause of AI synthesis failures.

The active immutable production database inspected read-only was:

```text
/home/chuck/.local/share/vocab-lexical/versions/wiktionary-20260901/lexical.sqlite
```

The relevant schema contains `entries`, `senses`, `forms`, `sounds`, `relations`, and an `entries_fts` FTS5 virtual table. `entries.entry_key` is the primary key. No ordinary index exists on `entries.normalized_lemma`.

The application performs:

```sql
SELECT *
FROM entries
WHERE normalized_lemma = ?
ORDER BY entry_key;
```

A representative read-only plan returned:

```text
QUERY PLAN
`--SCAN entries
```

The exact lemma path therefore performs a full table scan. The FTS table does not accelerate this ordinary equality predicate.

The smallest likely future correction during a dataset rebuild is:

```sql
CREATE INDEX idx_entries_normalized_lemma
ON entries(normalized_lemma);
```

A composite index should be added only if later query evidence demonstrates a matching composite access pattern. The active SQLite artifact was not modified.

## 13. Architecture alternatives

### Architecture A — Hardened current architecture

```text
canonical evidence
    -> code-owned candidates and partitions
    -> Ollama-constrained bounded judgments
    -> code-owned final assembly
    -> deterministic validator
```

- Code owns identity, candidate sets, topology assembly, final selection construction, Additional Meanings, and acceptance.
- The model owns paraphrase/summary language and bounded semantic choices.
- Ollama remains the runtime unless evidence justifies migration.
- Structural guarantees are strong when final assembly is code-owned.
- Semantic risk remains where a 20B generative model performs broad grouping or ranking.
- Latency and VRAM are moderate to high with `gpt-oss:20b`; swapping to an installed smaller model must be measured.
- Migration and operational complexity are lowest because the current provider path is retained.
- Choose if safer contracts and code assembly resolve failures without semantic-quality loss.
- Reject if grouping quality or latency remains unacceptable after contract hardening.

### Architecture B — Embedding-assisted smaller-model pipeline

```text
canonical senses
    -> deterministic projection
    -> sense embeddings
    -> similarity screening
    -> smaller model adjudicates ambiguous candidates
    -> code-owned topology
    -> deterministic validator
```

- Code owns projection policy, thresholds, candidate routing, topology, and acceptance.
- Embeddings provide screening/ranking evidence only.
- A smaller model owns bounded ambiguous judgments and learner language.
- Ollama/llama.cpp can serve the model; exact-word similarity needs no ANN.
- Structural guarantees remain strong because vectors and models do not directly construct accepted topology.
- Semantic risks include false merges/splits for short, figurative, archaic, or register-sensitive senses.
- Expected steady-state latency may be lower, but embedding generation/storage and model loading add complexity.
- Migration cost is moderate and requires a versioned embedding artifact.
- Choose if screening reduces model work while preserving difficult-category quality.
- Reject if thresholds are brittle or semantic recall falls materially.

### Architecture C — Specialized deterministic routing

```text
deterministic orchestrator
    -> deterministic rules / embedding screen
    -> small model or ranker
    -> stronger model only for unresolved ambiguity
    -> code-owned assembly
    -> deterministic validator
```

- Code owns routing, confidence policy, topology, escalation, and acceptance.
- Specialized learned components own only narrow judgments.
- `gpt-oss:20b` becomes a possible escalation model rather than the universal default.
- Structural guarantees are strongest if every route returns bounded evidence for code assembly.
- Semantic risk moves into routing thresholds and false confidence.
- On one 16 GB GPU, multi-model use may require sequential unloading/loading rather than concurrent residency; swap latency must be included.
- Implementation and operational complexity are highest.
- Choose only if measured escalation rates and quality justify the routing machinery.
- Reject if model swaps dominate latency or the simpler hardened architecture performs equivalently.

## 14. Final recommendation

> Move final topology assembly and final selection logic into deterministic code wherever practical. Learned models should answer bounded semantic questions over code-provided candidates. Preserve deterministic validation as the acceptance boundary. Do not assume GPT-OSS:20b is required for every semantic stage, do not treat embeddings as lexical truth, and do not migrate runtimes until controlled evidence shows a material benefit.

Specifically:

- retain Ollama for the next controlled experiment;
- retain `gpt-oss:20b` as the baseline and possible escalation model;
- test installed `qwen3:8b` first as the smaller-model challenger;
- test a code-assembled fixed-key/rank/score core contract against the current subset-array contract;
- investigate bounded or pairwise grouping only after the core contract is isolated;
- consider embeddings only as screening/ranking evidence;
- keep final validation deterministic regardless of model or runtime;
- treat the smaller-model hypothesis as empirical;
- do not approve multi-model routing until quality, escalation rate, model-swap latency, and operational cost are measured;
- do not pursue fine-tuning before contracts, diagnostics, and baseline comparisons are complete;
- do not introduce an autonomous multi-agent or "crew" architecture: the pipeline requires explicit deterministic orchestration and auditable task boundaries, not autonomous delegation.
