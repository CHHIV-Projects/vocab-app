# 1. Objective

M004.6.1 is the first empirical milestone following M004.6.0.

The objective is deliberately narrow:

> Determine how the deployed Ollama structured-output path behaves for the current core-selection contract, identify which individual contract predicates can fail, and determine whether a code-assembled fixed-key ranking contract is structurally safer without changing production synthesis.

This milestone should answer:

1. Can the current core-selection failure class be reproduced?
2. Does the deployed Ollama path permit duplicate enum-valid IDs because `uniqueItems` is not enforced?
3. Which malformed result classes are prevented by constrained decoding and which remain application-validator responsibilities?
4. Does a fixed-key ranking contract eliminate the current array/subset structural failure classes?
5. Do `gpt-oss:20b` and `qwen3:8b` behave differently on this narrow task?
6. Is the evidence strong enough to recommend a later production contract change?

This milestone is NOT:

- a production bug fix;
- a full lexical synthesis benchmark;
- a grouping redesign;
- an embedding experiment;
- a runtime bake-off;
- a model-download milestone;
- a broad model comparison;
- a frontend milestone.

# 12. Phase B — Fixed-Key Ranking Contract

Prototype one benchmark-only safer contract.

Do not implement multiple speculative alternatives.

Preferred design:

{
  "core_count": 3,
  "scores": {
    "G001": 5,
    "G002": 2,
    "G003": 4,
    "G004": 1
  }
}

The exact scoring scale may be adjusted if necessary, but keep it small and strongly constrained.

Required characteristics:

- every code-owned group ID is a schema property;
- every group ID is required;
- `additionalProperties: false`;
- scores come from a small bounded domain;
- `core_count` is constrained to `1..min(5, group_count)`;
- the model does not return arbitrary group IDs in an array;
- code deterministically creates the final core set.

Deterministic assembly should use:

1. descending score/rank;
2. stable code-owned tie-breaker;
3. `core_count`;
4. final IDs taken only from the code-owned candidate set.

This contract exists only in the benchmark harness.

Do not put it into production synthesis.
