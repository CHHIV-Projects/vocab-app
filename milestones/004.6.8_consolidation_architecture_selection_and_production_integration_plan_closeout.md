## 4. Architecture Decision

### Selected

```text
canonical source senses
  -> deterministic POS/material partition
  -> one-sense deterministic pass-through
  -> exhaustive eligible pair enumeration
  -> one bounded qwen3:8b judgment per pair
  -> Python-owned conservative complete-link clustering
  -> deterministic learner-meaning containers
  -> separate learner wording stage
  -> downstream Core/Additional ranking
  -> validation
  -> versioned persistence/cache
```

Initial Qwen policy:

- model: `qwen3:8b`;
- `think: false`;
- temperature `0`;
- deterministic seed policy;
- structured output;
- one eligible pair per semantic request;
- no model-generated IDs, groups, topology, or ranking.

### Rejected for production now

- global embedding threshold;
- embedding Top-K;
- deterministic structural screening as a correctness gate;
- bounded Qwen candidate proposal;
- autonomous multi-agent orchestration;
- corpus-wide precompute as the default.

These alternatives either missed approved merges or added complexity without enough safe reduction.

## 5. Target Consolidation Pipeline

1. Retrieve and freeze canonical evidence.
2. Compute evidence-set and lexical dataset identities.
3. Build deterministic POS/material partitions.
4. If a partition has one source sense, create one pass-through container.
5. Otherwise enumerate every eligible unordered pair in stable source-ID order.
6. Persist or resume pair judgments.
7. Require complete validated pair coverage before accepting topology.
8. Interpret `merge`, `keep_separate`, and `uncertain` using code-owned policy.
9. Build conservative complete-link containers.
10. Validate exact source-sense coverage and partition boundaries.
11. Generate learner wording from validated containers as a separate stage.
12. Run Core/Additional ranking after consolidation and wording.
13. Persist an immutable candidate/version snapshot and advance the active pointer only on explicit save.

## 6. Pair Judgment Contract

Proposed contract identity: `pair-judgment-v1-exhaustive-qwen`.

Input contains only code-owned context:

```json
{
  "task": "bounded semantic equivalence judgment",
  "word": "...",
  "pos": "...",
  "material_partition": [],
  "sense_a": {"source_sense_id": "...", "definition": [], "labels": [], "examples": [], "relations": []},
  "sense_b": {"source_sense_id": "...", "definition": [], "labels": [], "examples": [], "relations": []
  }
}
```

Output schema:

```json
{
  "decision": "merge | keep_separate | uncertain",
  "reason": "paraphrase_or_duplicate | contextual_variant | specialized_subsense | broader_or_narrower | related_but_distinct | materially_different | insufficient_evidence"
}
```

Validation requires exact top-level keys, allowed enum values, no extra fields, and a valid decision/reason combination. `uncertain` is never silently converted to `merge`; the initial conservative topology policy treats it as a blocked edge.

## 7. Pair Enumeration and Coverage Invariants

Python owns pair identity:

```text
pair_id = hash(
  consolidation_contract_version,
  partition_id,
  ordered(source_sense_id_a, source_sense_id_b)
)
```

This is the structural/logical pair ID only. The cached model judgment uses a separate identity:

```text
pair_judgment_identity = hash(
  logical_pair_id,
  evidence_identity,
  partition_identity,
  pair_judgment_contract_version,
  qwen_model_digest,
  semantic_options
)
```

Cached model output is keyed by `pair_judgment_identity`, never by the bare logical pair ID, so evidence, partition, model, or inference-contract changes cannot reuse stale judgments.

Rules:

- enumerate only within one POS/material partition;
- stable source-sense ordering;
- no self-pairs;
- each unordered eligible pair exactly once;
- no cross-POS or prohibited material merge;
- preserve exact source provenance;
- persist expected pair count and expected pair-ID set;
- finalization requires every expected pair to have exactly one compatible `succeeded_validated` semantic judgment;
- any retryable or terminal pair failure blocks normal topology finalization;
- a partial result cannot appear as a valid completed candidate.

## 8. Complete-Link Topology

Accepted merge edges are not blindly unioned. Start with singleton containers in stable source-sense ID order. Scan container pairs deterministically, merging only when every cross-container pair has a validated `merge` judgment; restart the scan after each merge until no eligible merge remains. A `keep_separate` or `uncertain` edge blocks the merge. Stable container IDs are generated from the sorted member IDs and contract identity.

Invariants:

- every source sense appears exactly once;
- no source sense disappears;
- no source sense occurs in multiple containers;
- no cross-POS/material merge;
- no model-generated container IDs;
- blocked/conflicting evidence is surfaced for review;
- false splits are preferred to unsafe false merges.

## 9. State Machine and Resume Semantics

### Pair state

```text
pending
  -> running/leased
  -> succeeded_validated
  -> failed_retryable
  -> failed_terminal
```

Only `succeeded_validated` counts toward complete semantic coverage. Leases expire conservatively; retryable failures may be retried with bounded backoff. Terminal failures prevent normal finalization and produce an explicit failed/escalated state.

### Consolidation job state

```text
created -> running -> complete_validated -> wording_pending -> ready
                         \-> failed/retry_available
```

Restart resumes from persisted pair state. Existing successful compatible judgments are not rerun. Duplicate requests converge on one logical work identity.

## 11. Cache and Version Identity

Use a dependency chain rather than one opaque identity:

```text
pair-judgment identity
  -> topology identity
  -> wording identity
  -> ranking/final-candidate identity
```

The pair-judgment identity is the `pair_judgment_identity` defined in Section 7. It includes normalized lemma, evidence and lexical-dataset identities, partition identity, `pair-judgment-v1-exhaustive-qwen`, Qwen model/digest, and semantic options. The topology identity hashes compatible pair-judgment identities plus `complete-link-v1` and `learner-containers-v1`. The wording identity hashes the topology identity plus `learner-wording-v1`. The ranking/final-candidate identity hashes the wording identity plus `core-ranking-v1` and the final candidate schema.

Hash each canonical identity without timestamps, request IDs, latency, or host details. A wording-only or ranking-only change therefore preserves compatible pair judgments; evidence, pair-contract, model, or semantic-option changes invalidate pair judgments, while topology changes invalidate topology and downstream stages.

## 12. M004.5 Save, Retry, and Refresh Integration

- **Save:** continues to accept one validated candidate/version and advances the active pointer atomically.
- **Retry:** reuses successful compatible pair judgments; retries only missing/retryable pair work and reruns wording only when needed.
- **Refresh:** preserves the current evidence-hash gate. Changed evidence creates a new candidate/job; the old saved version remains immutable.
- **Semantic rebuild:** should be a future distinct internal operation when model/contract changes without evidence changes. Do not overload the existing UI Refresh silently.
- **Failure:** no failed or partial consolidation is saveable as a normal accepted candidate.

## 13. Existing Data and Legacy Cache Strategy

Existing saved entries load immediately and are never silently regenerated because architecture changes. An explicit future refresh/rebuild may create a new version.

Unsaved legacy synthesis cache entries are not accepted history. Safest initial policy: treat them as versioned legacy results; display only if their contract is explicitly compatible, otherwise invalidate lazily and regenerate under the new contract. Do not migrate them in place.

## 14. Interactive versus Deferred Routing

Use measured Qwen p50/p95 latency and a configurable policy, not a hard-coded sense-count threshold.

Provisional initial UX policy:

- one sense: immediate deterministic pass-through;
- estimated p95 pair work up to approximately 10 seconds: interactive;
- above approximately 10 seconds and up to a bounded visible wait: interactive only with explicit processing state;
- minute-scale work: deferred/background job;
- cached valid result: immediate.

At the measured p95 of approximately 3.346 seconds per pair, ten senses (45 pairs) is approximately 150.6 seconds p95 and should not be synchronous. The initial configurable routing target should therefore be approximately 5–10 seconds p95, with the boundary derived from current latency measurements and revisited after production telemetry.

## 15. Background Processing Architecture

The smallest adequate future design is a persistent consolidation-job table plus one application worker/runner that claims pending jobs, executes pair work, and updates durable state. The worker must not depend on an ephemeral Streamlit session or in-memory request task: durable PostgreSQL job and pair state is authoritative, allowing an application/server restart to resume safely. It does not require a vector database, ANN service, or corpus-wide scheduler.

Foreground lookup for a deferred partition should:

1. return canonical evidence and a deterministic `generating` state;
2. create or attach to the idempotent consolidation job;
3. expose `ready`, `generating`, or `failed/retry_available`;
4. never expose a partial container as final.

Optional warming may target frequently searched or manually selected words. Full-corpus precompute is rejected initially.

## 16. Concurrency and Resource Policy

Initial recommendation: one Qwen lexical-consolidation inference at a time. Queue additional work. This minimizes VRAM pressure, provider instability, duplicate retries, and nondeterministic load interactions. Increase only after measurements demonstrate safe capacity.

Use one logical job identity per lemma/evidence/consolidation identity. Foreground/background races attach to the same job. Pair claims use short leases and idempotent unique keys. Save and refresh acquire the existing entry/version transaction boundary; no partial job can advance the active pointer.

## 17. Failure and Recovery Semantics

Classify provider outcomes separately:

- transport failure/timeout: retryable;
- empty/truncated response: retryable up to a bound;
- invalid JSON/schema: retryable, then terminal;
- valid `uncertain`: successful semantic result, but conservative blocked edge;
- persistent terminal failure: job failed/escalated and not saveable.

Every attempt retains request identity, raw response where available, parsed diagnostics, model identity, schema/prompt hashes, and timing. Restart resumes successful and pending state without rerunning valid work.

## 22. Architecture Decision Record

**Decision:** exhaustive bounded Qwen pair judgments with deterministic Python topology and versioned persistence.

**Rejected now:** global embedding threshold, embedding Top-K, deterministic structural screening, Qwen candidate proposal, and generic autonomous-agent orchestration.

**Rationale:** exhaustive pairwise Qwen is the only evaluated approach that preserved the approved merge reference without adding an unsafe screening authority. Most partitions are small, and successful results can be cached.

**Consequences:** rare large partitions require resumable persistence and asynchronous/background handling; normal cached lookup remains cheap; first-build latency and local inference capacity remain operational concerns.
