## 1. Objective

Establish a trustworthy, accepted learner-facing Vocab App baseline before introducing further local-AI product changes.

This milestone resumes the unfinished product acceptance originating in historical M004.5. The goals are to verify deployed-source parity, complete desktop/mobile browser lifecycle acceptance for Search, Save, saved-word reload, Retry, Refresh availability, Flag, and authoritative PostgreSQL reconciliation, verify durable immutable accepted versions, and establish the current GPT-OSS learner-synthesis behavior as the measured product baseline.

This is primarily an acceptance and baseline-establishment milestone. Do not redesign learner experience or AI architecture merely because another design may now be preferred.

## 12. Required Desktop Browser Acceptance

Using safe disposable test data, validate:

### Fresh Search
Confirm query resolution, valid learner candidate, Core/Additional meanings, labels, IPA/audio state, Source Details, forms/base links, synonyms, etymology, Advanced Details, and no uncaught exception. Record approximate latency; do not impose a new performance target.

### Unsaved Candidate Actions
Confirm correct action state, including Save/Flag and correct disabling/hiding of non-applicable actions.

### Save
Confirm UI reports durable accepted state only after persistence succeeds, Save becomes unavailable as appropriate, accepted version exists in PostgreSQL, candidate/evidence identities are durable, expected practice projection behavior occurs, no partial rows remain after failure, and accepted version reloads through a fresh persistence connection.

### Reload / Fresh Session
Confirm saved accepted version loads, PostgreSQL remains authoritative, stale session state cannot create a false Saved state, and saved-version loading avoids unnecessary fresh semantic generation where current architecture says it should use the accepted version.

### Retry
Confirm Retry uses the exact stored evidence snapshot, does not silently substitute newer evidence, can create a new candidate without destroying the prior accepted version, and preserves history. If a retried candidate is saved with disposable data, verify new version number, retained old version, and active-version pointer moves only after successful Save.

### Refresh
Do not alter lexical data merely to force Refresh. For unchanged evidence, confirm Refresh is unavailable/disabled. Changed-evidence behavior may remain covered by deterministic fixtures/tests if inducing live change would require lexical-dataset mutation. Distinguish browser-observed unchanged-evidence behavior from automated changed-evidence behavior.

### Flag
Confirm one-click Flag persists, repeat Flag is idempotent, and Flag does not alter accepted lexical evidence/version contents.

## 15. Bounded Defect Correction Policy

A defect may be corrected only when:
1. it prevents acceptance of behavior already implemented/intended by M004.5 or current governing architecture;
2. root cause is sufficiently understood;
3. correction is narrow;
4. correction does not redesign AI semantics;
5. correction does not alter source lexical authority;
6. correction does not introduce new product behavior;
7. focused regression evidence can validate it.

Potentially in scope: browser rendering type bug, stale-state reconciliation defect, incorrect action state, persistence row-shape bug, bounded deployment packaging omission, or a test fixture that demonstrably misrepresents production semantics.

Out of scope: new semantic grouping architecture, new AI model, Qwen work, prompt tuning, embeddings, UI redesign, practice redesign, translation provider replacement, lexical-index rebuild, or broad persistence redesign.

If a defect requires broader change, stop and escalate rather than expanding scope.
