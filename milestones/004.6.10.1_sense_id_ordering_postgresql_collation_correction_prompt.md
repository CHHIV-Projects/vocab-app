# 2. Why This Corrective Milestone Exists

During M004.6.12 live integration testing, a PostgreSQL `CHECK` constraint failure exposed a mismatch between:

- Python's canonical source-sense ordering using normal `sorted()` / Unicode code-point ordering; and
- PostgreSQL text `<` comparison under the database's locale collation (`en_US.utf8`).

Read-only corpus characterization established that this is systemic, not an isolated word-specific issue.

Observed scope:

- total lexical senses: approximately 1,894,561;
- senses containing the anomalous list-like source-ID form: 24,722 (~1.3%);
- affected POS entries containing those IDs: 15,245;
- same-entry sense pairs examined: 285,919;
- Python-vs-PostgreSQL ordering disagreements: 67,349 pairs;
- POS entries containing at least one ordering disagreement: 6,922;
- approximately 0.44% of all POS entries;
- roughly 1 in 230 real POS entries could encounter the current persistence constraint defect.

Example anomalous sense-ID shape:

`['en:Q15872']`

The anomaly itself may originate upstream, but M004.6.10 persistence must be able to store any valid canonical source-sense ID produced by the accepted lexical evidence pipeline.

The immediate defect is therefore:

> The database attempts to enforce the same canonical source-pair ordering as Python, but it currently uses locale-aware text comparison whose ordering semantics differ from Python's canonical ordering.

This milestone corrects that persistence invariant.

# 3. Architectural Principle

**Python Unicode/code-point ordering as produced by the existing deterministic pair enumeration.**

PostgreSQL must enforce that SAME ordering semantics.

Do NOT change Python pair ordering merely to match the host database locale.

Database locale must not determine semantic/persistence identity.

The invariant should be:

Python canonical ordered pair
    ==

- punctuation;

- digits;
- ASCII/non-ASCII content;
- list-like source-ID strings currently present in the lexical dataset.
