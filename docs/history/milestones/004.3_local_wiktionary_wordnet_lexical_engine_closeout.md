## 3. Implemented lexical-data layout

The implementation supports a host-oriented version layout conceptually equivalent to:

```text
<LEXICAL_DATA_ROOT>/
  versions/<dataset-version>/
    manifest.json
    evidence.jsonl
    lexical.sqlite
  active
```

`resolve_active_database()` supports one configured active pointer file containing a version name. A future deployment may instead use an atomic symlink, but M004.3 does not implement competing activation mechanisms or hard-code an operator path.

Fixture tests use temporary directories. No lexical data is copied into the application image.

## 4. Manifest/version strategy

`build_manifest()` records:

- source type;
- dataset version;
- source URL/identifier;
- source snapshot description;
- captured language codes `en` and `mul`;
- importer version;
- schema version;
- input SHA-256;
- normalized JSONL SHA-256;
- attribution/license reference;
- normalized record count.

The fixture dataset version used for tests is `fixture-20260906`. The importer version is `m004.3-v1`; the normalized evidence schema is `lexical-evidence-v1`.

## 5. Wiktextract ingestion/normalization design

`normalize_jsonl()` accepts Wiktextract-compatible JSONL and writes canonical JSONL records without GPT-OSS or external dictionary calls.

Normalization preserves:

- word and normalized lemma;
- language/language code;
- part of speech;
- source record and source-record hash;
- source locator including fixture path/line;
- dataset/importer/schema versions;
- multiple senses and source order;
- glosses, raw glosses, tags, topics, examples;
- forms;
- sounds/IPA/audio metadata;
- etymology text/templates;
- lexical relations.

Records outside the initial `en`/`mul` scope are ignored. Missing source fields remain missing.

## 6. Stable evidence-ID implementation

Entry identity is derived from canonical source identity components including word, language, POS, etymology number, and source-record hash. Sense identity uses the source `senseid` when supplied; otherwise it uses a deterministic hash of canonical sense content.

Evidence IDs include source, dataset version, importer version, language, entry key, sense key, and field/relation identity, for example:

```text
WIK:<dataset>:<importer>:<language>:<entry>:<sense>:sense
WIK:<dataset>:<importer>:<language>:<entry>:<sense>:<relation>:<target-hash>
```

No JSONL line number, SQLite row ID, import order, or runtime insertion order is used as provenance identity. Source locators and source-record hashes remain available for audit.

## 7. SQLite/FTS5 schema and lookup behavior

`build_sqlite()` creates a replaceable projection with:

- `entries`;
- `senses`;
- `forms`;
- `sounds`;
- `relations`;
- `entries_fts` FTS5 projection.

Every entry retains evidence identity, dataset version, importer version, source locator, source-record hash, and canonical source-record JSON. SQLite IDs are not exposed as provenance.

`lookup()` performs exact case-folded normalized lemma lookup and returns all matching entries and senses, plus a separate WordNet evidence collection. FTS5 exists as a secondary projection and is not required for exact dictionary lookup.

## 8. WordNet parallel evidence behavior

`wordnet_evidence()` returns a separate collection of WordNet synset IDs, POS values, glosses, and sorted lemma names. It is not merged with Wiktionary senses or relations.

The implementation does not claim Wiktionary-to-WordNet sense alignment. The host test environment may lack NLTK; in that environment the parallel collection is empty. The configured operational environment supplies WordNet as established by M004.1.

`wordnet_version()` derives a reproducible identity from the installed NLTK version plus a SHA-256 fingerprint of sorted WordNet resource-relative paths and file contents. The filesystem location is not included in the identity; it is only a diagnostic input to locate the resources. The same resource contents at different host paths produce the same fingerprint, while content changes produce a different identity.

## 9. Evidence-bundle representation

`evidence_bundle()` produces a deterministic bundle containing lexical entries and separate WordNet evidence. The bundle is suitable for later retention with accepted application entries but is not persisted to PostgreSQL in M004.3.

## 10. Canonical serialization and `evidence_set_hash`

`canonical_json()` uses UTF-8 JSON with sorted object keys and compact separators. The evidence hash is SHA-256 over that canonical serialization.

Meaningful evidence changes alter the hash. Object key ordering does not. Source sense lists retain source order; entry lookup order is deterministic by entry identity. No runtime timestamp, SQLite row ID, set iteration order, or incidental filesystem path is included in the bundle hash.

3. Run Wiktextract with English/translingual capture configuration and recorded tool versions.

5. Build `lexical.sqlite` and verify SQLite integrity and representative lookups.
6. Run resource/latency checks and compare against the approval estimates.

Rollback is an active-pointer switch to the prior verified version; failed new builds are removed only after preserving logs and the prior active version.
