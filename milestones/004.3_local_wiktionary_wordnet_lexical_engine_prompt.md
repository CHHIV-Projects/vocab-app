# 5. Lexical artifact layout

Design and implement a host-oriented versioned lexical-data layout.

The lexical dataset must remain:

- outside Git;
- outside the normal Vocab application image;
- independently replaceable;
- versioned;
- readable by the future application runtime;
- suitable for atomic active-version switching.

A conceptual layout may resemble:

```
<lexical-root>/    versions/        <dataset-version>/            manifest.json            evidence.jsonl            lexical.sqlite            attribution/    active -> versions/<dataset-version>
```

This layout is illustrative.

Choose the smallest clean implementation appropriate to the repository and runtime.

Do not hard-code an operator-specific production path into source code.

Use configuration/environment boundaries where required.

# 7. Wiktextract ingestion boundary

Implement a bounded ingestion path that accepts Wiktextract-compatible JSONL.

The importer must not depend on GPT-OSS or another model.

The importer should normalize relevant source records into the canonical lexical evidence shape approved in M004.2.

At minimum preserve, where supplied:

```
LexicalEntry    lemma    normalized lemma    language    source language    source metadata    source locatorSense    source sense identity    part of speech    glosses    usage labels    examples    source orderForm    spelling/form    grammatical tagsPronunciationEvidence    IPA    dialect/region tagsEtymologyEvidence    source etymology text/dataSemanticRelation    relation type    target term    source identity
```

Missing data must remain missing.

Do not synthesize absent evidence.

Do not use AI to repair source records.

# 8. Stable evidence identity

Implement a deterministic evidence-identity strategy.

Evidence identity must distinguish at least:

- source;
- dataset version;
- importer/schema version;
- language;
- lexical entry;
- sense where applicable;
- field/relation.

Do not use:

- JSONL line number;
- SQLite row ID alone;
- import ordering;
- another unstable positional identity.

The M004.2 conceptual pattern was:

```
WIK:<dataset-version>:<importer-version>:<language>:<entry-key>:<sense-key>:<field>WN:<wordnet-version>:<synset-id>:<relation>
```

The exact encoded form may differ.

If hashes are used, the underlying identity components must remain inspectable.

Record source locators and record hashes where practical.

# 9. SQLite / FTS5 lexical index

Implement the replaceable local SQLite/FTS5 lookup index.

The SQLite database is a runtime lookup acceleration structure.

It is NOT the sole canonical evidence artifact.

The versioned JSONL evidence artifact remains independently recoverable.

The index should support at minimum:

- exact normalized lemma lookup;
- retrieval of all relevant English entries for a lemma;
- multiple parts of speech;
- multiple senses;
- forms;
- pronunciation evidence;
- etymology evidence;
- lexical relations;
- source/evidence IDs.

Use FTS5 only where it provides concrete value.

Do not overbuild general-purpose search functionality merely because FTS5 is available.

Exact dictionary lookup is the primary M004.3 requirement.

# 10. Local lexical query boundary

Create or extend a small application-independent lexical query boundary.

The caller should be able to request a word and receive deterministic structured evidence.

Conceptually:

```
lookup("running")
```

should return something equivalent to:

```
lemmaentries    POS    senses        glosses        labels        examples        evidence IDs    forms    pronunciation    etymology    lexical relationssource/version metadata
```

Do not make Streamlit responsible for SQLite schema knowledge.

Do not embed raw SQL throughout `app.py`.

Keep the lexical-store/query boundary independently testable.

# 11. Preserve multiple senses

Do not reproduce the current first-WordNet-synset limitation.

A lookup must preserve materially distinct source senses.

Use `running` / `run` as an important acceptance case.

The deterministic engine should make the underlying evidence available for senses such as those represented in the source dataset, potentially including:

- movement on foot;
- operating/functioning;
- managing/directing;
- flowing;
- continuing/ongoing;
- noun/activity meanings.

Do not fabricate these senses if the fixture/source does not provide them.

The requirement is to preserve multiple source senses, not to force a predetermined dictionary answer.

Do not use AI to decide which senses are common in M004.3.

Source ordering and metadata should remain available for M004.4 synthesis.

# 12. WordNet parallel evidence

Preserve the existing WordNet capability but expose it through the lexical-engine architecture as parallel supplemental evidence.

At minimum make it possible for a lexical result to contain:

```
Wiktionary evidence    ...WordNet evidence    synset IDs    glosses where needed for source comparison    synonyms/lemmas    semantic relations where currently practical
```

Do not merge a Wiktionary sense and WordNet synset into a single canonical sense unless there is explicit deterministic evidence for the mapping.

For M004.3, this is acceptable:

```
Wiktionary senses    independent evidenceWordNet synsets    independent evidence
```

Future M004.4 synthesis can reason over both while preserving provenance.

# 13. Canonical evidence bundle

Implement and test a deterministic representation of the small evidence bundle that may later be retained with an accepted vocabulary entry.

Do NOT add PostgreSQL tables yet.

Given a lexical lookup result, code should be able to produce a frozen canonical evidence bundle containing the exact relevant normalized evidence.

The bundle should be suitable for future retention of:

- Wiktionary entry evidence;
- senses/glosses;
- forms;
- etymology;
- pronunciation;
- lexical relations;
- relevant WordNet evidence;
- evidence IDs;
- source versions;
- importer/schema versions;
- source locators;
- source-record hashes.

Define a deterministic canonical serialization.

Compute:

```
evidence_set_hash
```

from that canonical serialization.

The same evidence in the same canonical order must produce the same hash.

Ordering differences that are not semantically meaningful must not randomly alter the hash.

Do not persist the bundle to PostgreSQL in M004.3.
