## 4. Defect

- Table: `lexical_pair_judgments` (introduced by migration `003_m004610_consolidation_persistence.sql`).
- Constraint: `lexical_pair_judgments_source_ids_ordered`
  ```sql
  CHECK (
      btrim(source_sense_id_a) <> '' AND btrim(source_sense_id_b) <> ''
      AND source_sense_id_a < source_sense_id_b
  )
  ```
- Columns: `source_sense_id_a`, `source_sense_id_b` (both `TEXT`).
- Python canonical ordering authority: `SensePair.create()`'s `sorted((first, second))` in
  [vocab_consolidation.py](/home/chuck/projects/vocab-app/vocab_consolidation.py) — Unicode
  code-point ordering.
- PostgreSQL's default `<` comparison uses the database's **default locale-aware collation**
  (`en_US.utf8` in the disposable containers used here, and presumptively in any standard
  PostgreSQL install). For real source sense IDs containing punctuation such as `[`, `]`, `'`
  (see Section 6), this locale-aware ordering **disagrees** with Python's code-point ordering,
  so a pair that Python considers canonically ordered (`source_sense_id_a < source_sense_id_b`
  is `True` in Python) is rejected by the database CHECK (`False` in PostgreSQL), or vice versa.
- Concretely reproduced on the real `gecko` noun partition: entry `c922e763649711dfbac25110`
  has two senses whose IDs differ only in the segment `content` vs. `['en:Q15872']`. Python
  ranks the `['en:Q15872']` form as smaller (`[` = 0x5B < `c` = 0x63); PostgreSQL's default
  collation ranks it larger.

## 6. Root Cause

PostgreSQL's default collation (`en_US.utf8`) applies locale-aware, linguistically-informed
text ordering — for example, punctuation characters are frequently ignored, downweighted, or
reordered relative to alphanumeric characters, and case/accents are folded according to
locale-specific tailoring rules. Python's `<` for `str` (and `sorted()`) instead performs
**pure Unicode code-point ordering** with no locale awareness at all. The M004.6.10 schema's
`CHECK (source_sense_id_a < source_sense_id_b)` implicitly assumed these two orderings would
always agree. That assumption held for every synthetic fixture used during M004.6.9/M004.6.10/
M004.6.11 development (plain alphanumeric identifiers), but breaks for real Wiktionary-derived
sense IDs that embed upstream artifacts such as a stringified Wikidata category list
(`['en:Q15872']`) directly in the ID — content the M004.6.x milestones treat as an opaque
identifier and are not permitted to rewrite or normalize (Section 13 of the governing prompt).

## 7. Chosen Correction

Replace the plain `<` comparison with an explicit `COLLATE "C"` comparison on both operands:

```sql
(source_sense_id_a COLLATE "C") < (source_sense_id_b COLLATE "C")
```

`"C"` (equivalently `POSIX`) is PostgreSQL's byte-order/code-point collation, which performs a
raw byte-wise comparison of the UTF-8 encoding — for the all-ASCII structural characters used
in these sense IDs, this is equivalent to Python's Unicode code-point ordering. This was
verified empirically, not just theoretically: the full corpus re-verification (Section 14)
shows **zero** disagreements between Python ordering and `COLLATE "C"` ordering across all
1,133,467 same-entry pairs, versus 67,349 disagreements under the database's default collation.
Both `"C"` and `POSIX` collations were confirmed available in the PostgreSQL 17.11 runtime
used for all validation.
