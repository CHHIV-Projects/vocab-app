## 5. Job Model

`ConsolidationPersistence.create_or_get_job()` stores one deterministic
`consolidation_identity` per partition computation. Its canonical identity includes the
normalized lemma, evidence hash, lexical dataset identity, partition identity, pair
contract, semantic model/options identities, and topology/container contracts. A database
surrogate key is used only as a relational reference.

Jobs support `created`, `running`, `failed_retryable`, `failed_terminal`, and
`topology_validated`; the latter requires topology identity and completion time. Progress
is derived from pair rows by `job_progress()`, rather than maintained as a divergent
denormalized counter.

## 6. Pair Judgment Model

Every pair row persists separately queryable:

```text
partition identity
-> logical_pair_id
-> pair_judgment_identity
-> validated_result_identity
```

It also stores canonical source IDs, evidence hash, judgment contract, model/options
JSONB, durable status, bounded retry/lease metadata, and last failure classification and
summary. No provider request or raw response is fabricated. The schema prevents duplicate
logical pairs and duplicate judgment identities within one job.

## 7. Container Model

Final containers persist their partition, topology and container identities, JSONB ordered
source-sense membership, and container contract. `finalize_topology()` reconstructs
M004.6.9 `PairJudgment` objects, invokes coverage validation and deterministic
complete-link topology, persists containers, and marks the job `topology_validated` in one
transaction. Python remains responsible for semantic compatibility and exact cross-container
source coverage; SQL protects row shape, uniqueness, and foreign keys.

## 8. Job/Partition Granularity Decision

The implementation uses **one job per deterministic partition**. This directly matches
M004.6.9's partition-local pair enumeration and topology identities, makes every pair's
partition unambiguous, and lets a word with multiple POS/material partitions be resumed
without an ambiguous aggregate job state.

## 9. State Transitions

Pair transitions are enforced by the persistence API:

```text
pending -> running -> succeeded_validated
                  -> failed_retryable -> running
pending/running/failed_retryable -> failed_terminal
```

Successful and terminal rows cannot be claimed again. A successful row can only be
re-submitted idempotently with the identical decision, reason, and result identity.

## 10. Idempotency

Unique consolidation identity plus conflict-safe create-or-get converges duplicate requests
to the same job. Repeated initialization inserts expected partition pairs with conflict-safe
inserts, then verifies the stored logical pair set exactly equals the immutable M004.6.9
enumeration. An incompatible partition manifest is rejected.

## 11. Successful Judgment Immutability

`store_validated_judgment()` locks the pair row and rejects a different successful result
for the same semantic input. It does not use last-write-wins behavior.

## 12. Resume Semantics

`list_incomplete_jobs()` exposes unfinished jobs. `list_resumable_pairs()` exposes pending,
retryable, and expired-running pair work. Validated rows remain reusable, terminal failures
remain discoverable in the ledger, and completed jobs expose only persisted final containers.
Lease owner/acquired/expiry and attempt count are stored for a later worker, but no worker
is implemented.

## 13. Coverage / Finalization Transaction

Finalization locks the job, loads durable successful pair rows, reconstructs the unchanged
M004.6.9 identity hierarchy, and runs the existing coverage validator plus complete-link
assembler. Missing, pending, retryable/terminal, foreign, or incompatible rows cannot
publish a topology. Any validation exception rolls back the transaction, so no partial
containers or completed job state can persist.

## 14. One-Sense Behavior

A one-sense partition initializes zero pair rows and finalizes to one deterministic
container without provider work.

## 15. Complete-Link Persistence

The persistence tests include the M004.6.9 non-transitive fixture:

```text
A-B = merge
B-C = merge
A-C = keep_separate
```

It persists the exact safe `{A,B}` plus `{C}` topology rather than a transitive
three-sense merge. An `uncertain` validated result is coverage-complete but produces
separate containers.

## 17a. Architect-Directed Production Code Restoration and Escalated Finding

Following Product Owner / Architect review, incidental changes made to the live,
already-accepted `vocab_persistence.py` module during earlier M004.6.10 debugging were
restored to their exact pre-M004.6.10 (HEAD) behavior:

- removed `_mapping_row(...)`;
- removed the added `with self.connection.transaction():` wrappers from
  `_verify_durable_version()` and `load_active_version()`;
- restored the original unconditional candidate-identity hash computation in
  `save_accepted_version()`;
- removed the added unconditional `self.connection.commit()` from
  `save_accepted_version()`.

`vocab_persistence.py` is now byte-identical to the version at HEAD. This milestone makes
**no production persistence code changes**.

Instead, `tests/test_m0045_postgres_isolated.py` was corrected to open its disposable
PostgreSQL connections with `row_factory=dict_row`, matching the row shape already used by
`PostgresPersistence.from_env()` in production, and the test's own raw-cursor assertions
were updated from tuple-style (`row[0]`) to dict-style (`row["column"]`) access to match.
This is a test-harness-only change; it does not alter production behavior.

After these corrections, rerunning the full targeted suite against a fresh disposable
PostgreSQL 17.11 database produced **one failure**, isolated entirely to a pre-existing
M004.5 test:

```text
FAIL: test_save_returns_durable_accepted_version_after_new_connection
AssertionError: 'dc9ecb9e8c9feeff59b7ecd7305e7978a792e8a66e4b69fe72dd7b9219e4a087' != '23efbb303ab8b23ff5f1ed07d35cc765e1862a06a111bdd5b8c508518483ce19'
```

**Root cause (reproduced deterministically, independent of row shape or transaction
boundaries):** the test constructs a `candidate` dict containing a `"candidate_identity":
None` key, computes a SHA-256 hash over the entire dict (including that `None` value) via
`json.dumps(candidate, sort_keys=True, ...)`, and then assigns that hash back into
`candidate["candidate_identity"]` before calling `save_accepted_version(candidate, ...)`.
Production's unconditional identity computation (`hashlib.sha256(json.dumps(candidate,
...))`, unchanged since HEAD) re-hashes the same dict a second time, but by then the dict's
`candidate_identity` field holds the previously computed hash string instead of `None`.
Hashing a payload that includes its own previous hash as a field necessarily produces a
different digest, so `saved["candidate_identity"]` can never equal the test's precomputed
`candidate["candidate_identity"]`. This is a self-referential test construction defect, not
a database, row-shape, or transaction-visibility issue. It was verified by recomputing both
hashes directly in Python outside of any database interaction, which reproduced the
mismatch exactly.

This defect predates M004.6.10: `git log` shows the test method was introduced with the
original M004.5 milestone commit and gated behind `M0045_TEST_DATABASE_URL`, so it had
apparently never been executed against a live PostgreSQL database before this milestone's
validation work exercised it for the first time.

Per the Architect's directive, this failure is **not** solved inside M004.6.10 by
reintroducing the removed override/transaction/commit changes. It is reported here for a
separately authorized M004.5 correction decision.

**Escalation summary:**

- Exact failing test: `tests.test_m0045_postgres_isolated.IsolatedPostgresM0045Tests.test_save_returns_durable_accepted_version_after_new_connection`
- Traceback: `AssertionError` on `self.assertEqual(saved["candidate_identity"], candidate["candidate_identity"])` at line 79.
- Database state involved: none required to reproduce; the mismatch is deterministic and reproducible with plain Python hashing, no PostgreSQL interaction needed.
- Classification: **test-construction defect** (self-referential hash input), not read visibility, not transaction state, and not a genuine candidate-identity production defect.
