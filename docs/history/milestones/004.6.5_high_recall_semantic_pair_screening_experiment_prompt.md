# 1. Objective

M004.6.5 follows the completed and adjudicated M004.6.4 benchmark.

M004.6.4 established:

- the refined bounded consolidation contract is materially better calibrated than the earlier same/distinct-only framing;
- Qwen3:8b with benchmark-local `think: false` is currently the strongest measured single-pair consolidation candidate;
- on the adjudicated reference, Qwen single-pair achieved:
  - 94.6% reference agreement;
  - 100% recall on the six resolved merge-reference pairs;
  - zero false splits;
  - three false merges;
- GPT-OSS remains useful but over-merges more often;
- batch-5, batch-10, batch-20, and anchor strategies reduce request counts but degrade semantic quality too much for primary production use;
- complete-link conservative code-owned clustering remains preferred;
- exhaustive single-pair evaluation does not scale acceptably to large polysemous partitions;
- embeddings were previously deferred because there was not yet enough semantic evidence to justify them.

That justification threshold has now been substantially met.

The objective of M004.6.5 is:

> Determine whether a cheap semantic screening stage can eliminate a large majority of obviously non-merge sense pairs while preserving essentially all validated merge candidates, so that the strongest measured single-pair consolidation method can be retained without exhaustive all-pairs cost.

The proposed architecture under test is:

canonical source senses
    ->
deterministic POS/material partitioning
    ->
semantic pair screening
    ->
small candidate pair set
    ->
Qwen single-pair bounded merge judgment
    ->
conservative code-owned complete-link clustering
    ->
learner-meaning containers

The screener must NEVER decide that two senses should merge.

Its only permitted decision is:

> Is this pair plausible enough that the bounded semantic model should inspect it?

This milestone should answer:

1. Can embeddings or another cheap similarity representation retain all validated merge-reference pairs?
2. How many non-merge pairs can be safely eliminated?
3. What similarity threshold or top-K policy is needed?
4. How sensitive are results to threshold selection?
5. Does screening materially reduce large-partition pair counts?
6. Is the infrastructure/storage/versioning cost justified by the reduction?
7. Is one embedding model sufficient?
8. Does screening preserve difficult lexical relationships, not merely near-identical wording?
9. Is the resulting screened-Qwen pipeline practical enough to move toward production architecture planning?
10. If not, should embeddings be rejected and another architecture explored?

This milestone is NOT:

- production embedding integration;
- production grouping implementation;
- production UI work;
- a vector search feature;
- semantic word search;
- learner Core Meaning ranking;
- frequency/commonness analysis;
- model fine-tuning;
- a broad model bake-off;
- a vector database deployment.

# 6. Architectural Principle

The screening stage must obey:

> Screening may remove obviously implausible merge candidates from expensive semantic review, but it must never become merge authority.

The screener MAY answer:

- compare with semantic model;
- skip semantic comparison.

The screener must NOT answer:

- merge;
- same learner meaning;
- same container;
- accepted semantic equivalence.

Only the bounded semantic model may provide positive merge evidence.

Only Python may construct accepted topology.

---

# 7. Success Standard

This experiment should optimize for HIGH RECALL of true merge candidates.

The primary safety rule is:

> Missing a true merge candidate at screening time is worse than retaining extra non-merge pairs.

The initial success target is:

- **100% retention of resolved Product-Owner/Architect-approved merge-reference pairs**, and
- **>=80% reduction of resolved keep-separate candidate comparisons**, if achievable without brittle thresholding.

If 100% merge retention cannot be achieved, the screener is not acceptable under the current reference.

If 100% retention is achievable but comparison reduction is materially below 80%, assess whether the infrastructure is still worthwhile.

Do not manipulate thresholds merely to hit the target without reporting sensitivity and tradeoffs.

# 14. Top-K Screening Alternative

Threshold-only screening may behave poorly on different words or sense-count distributions.

Also test a simple per-sense top-K candidate strategy.

Examples:

- each sense retains top 2 most similar peers;
- top 3;
- top 5.

Construct the undirected retained-pair set from these code-owned candidate lists.

Measure:

- merge-reference recall;
- keep-separate reduction;
- pair-count reduction;
- sensitivity to K.

Do not test excessive K values.

This gives us an alternative to one global threshold.

---

# 15. Hybrid Threshold + Top-K Safety

Optionally test ONE simple hybrid:

> retain any pair above threshold OR within each sense's top-K nearest peers.

This is attractive because:

- threshold catches obvious semantic closeness;
- top-K protects unusual but valid senses from isolation.

Evaluate whether this materially improves merge recall without destroying comparison reduction.

Keep it simple.

Do not create a complicated heuristic pipeline.

# 22. False-Split Risk

Because the code merges only with positive semantic evidence:

- screening-out a true merge pair creates a false split;
- it cannot create a false merge directly.

This is why recall is the primary screening metric.

Explicitly report:

- number of validated merge pairs lost by screening;
- which pair IDs;
- their similarity;
- why they may be difficult.

Any lost resolved merge pair is a failed safety condition under the initial acceptance target.

---

# 23. False-Merge Boundary

Screening itself cannot authorize a merge.

Therefore:

- embedding false positives primarily cost extra Qwen calls;
- embedding false negatives create semantic fragmentation.

The experiment should optimize accordingly.

Do not optimize for classification accuracy in the abstract.

Optimize for:

> near-perfect merge-candidate recall with maximum safe comparison reduction.
