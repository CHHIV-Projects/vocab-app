# A. Preserve Accepted Semantic Rules

Do not change these decisions:

- one canonical source sense = one learner meaning by default;
- do not semantically merge separate source senses;
- meanings remain grouped by POS;
- initial display is up to five meanings total per word;
- ensure at least one meaning from each represented POS where practical;
- fill remaining initial slots in deterministic source order;
- remaining senses are Additional meanings;
- labels are displayed but are not treated as frequency/popularity;
- synonyms are per sense;
- etymology is source-derived;
- U.S. pronunciation only;
- saved versions are immutable;
- no automatic saved-word refresh;
- newer dataset refresh is explicit and creates a new candidate/version path;
- no AI, embeddings, heuristic semantic consolidation, or inferred popularity ranking.

If a product-quality problem appears to require violating one of these rules, STOP and raise a bounded Repo Control question instead.

---

# B. Representative Real-Word Product Trial

Build and execute a deliberate real-data acceptance corpus large enough to expose presentation problems without becoming another research project.

Target approximately 20–30 words spanning:

- simple single-sense entries;
- ordinary multi-sense entries;
- highly polysemous entries;
- multi-POS entries;
- inflected/form-of entries;
- entries with usage labels;
- entries with per-sense synonyms;
- entries with one etymology;
- entries with multiple etymology sections where available;
- entries with U.S. IPA;
- entries requiring TTS fallback where applicable;
- entries with sparse or awkward Wiktionary gloss structure;
- at least several words previously useful in acceptance such as `aardvark`, `book`, `run`, `running`, and `lantern`.

Use the installed lexical dataset read-only.

Record enough evidence in the workflow/closeout to show what classes were tested and what defects were found.

Do not create a new semantic benchmark or human-adjudicated truth set.

# C. Learner Definition Presentation

Evaluate the visible meaning presentation as a learner would encounter it.

Correct bounded formatting/usability problems such as:

- duplicated gloss fragments;
- repeated parent/context text;
- raw source markup leaking into the learner view;
- awkward punctuation/whitespace;
- confusing hierarchy display;
- labels placed where they are hard to associate with the sense;
- unclear POS grouping;
- Additional meanings that are difficult to discover or navigate;
- overly technical metadata in the primary view;
- source-derived text presented in a way that obscures the actual definition.

Allowed changes are deterministic formatting/presentation changes.

Do NOT rewrite source meanings into new prose or infer a better definition.

If source content itself is poor and cannot be safely improved deterministically, preserve it and document the limitation.

---

# D. Initial vs. Additional Meanings UX

Verify the approved five-total policy across real multi-POS words.

Acceptance should establish that:

- the initial learner view remains compact;
- each represented POS receives at least one initial meaning where practical;
- source order is deterministic;
- expanding Additional meanings is obvious;
- expanding does not lose POS grouping or source-sense identity;
- collapsing/expanding behaves consistently on desktop and mobile;
- terminology does not imply frequency evidence the app does not possess.

Prefer learner-facing wording such as **Meanings** / **Additional meanings** unless existing terminology is already equally clear.

---

# E. Synonym Presentation

Review real entries with sense-bound synonyms.

Polish so that:

- synonyms are visibly associated with the correct meaning;
- the UI does not imply word-level synonym equivalence across unrelated senses;
- long synonym lists do not overwhelm the definition;
- absence of synonyms does not create awkward empty UI;
- source provenance remains available in secondary details;
- no synonym inference is added.

---

# F. Etymology Presentation

Review source-derived etymology in real entries.

Polish deterministic rendering for:

- readable paragraph/list structure;
- multiple etymology boundaries;
- source templates/text artifacts;
- excessive default vertical space;
- expand/collapse behavior where long;
- mobile readability.

Do not generatively summarize, combine, or reinterpret etymologies.

If templates cannot be rendered safely, prefer transparent source-derived text over invented cleanup.

---

# G. Pronunciation / Audio UX

Verify the U.S.-only pronunciation presentation.

Check:

- U.S. IPA placement;
- behavior when U.S. IPA is absent;
- existing gTTS/audio control placement and state;
- no misleading non-U.S. pronunciation presentation;
- mobile tap usability.

Do not broaden pronunciation scope.

External gTTS calls need not be exercised if doing so would introduce unnecessary external dependency during automated acceptance; test the control/path safely and document any live-call limitation.

---

# H. Save / Saved Entry / Flag Experience

Exercise the actual app using an isolated disposable PostgreSQL test database.

Verify:

- Save is obvious on an unsaved candidate;
- Save creates an immutable accepted version;
- the app clearly indicates saved state after reload;
- reopening a saved word returns the saved snapshot;
- saved entries do not silently change with current lexical evidence;
- Flag remains simple and usable;
- no AI-era model/prompt concepts leak into the normal current learner UI;
- a newer dataset identity does not automatically refresh a saved entry;
- explicit Refresh remains available only under the accepted newer-dataset condition and preserves version history.

Do not use or mutate production learner records for automated testing.

If Product Owner later chooses to test production manually, that is separate acceptance evidence.

---

# I. Dataset Status / Update Surface

Review the installed lexical dataset status control for clarity.

The learner should be able to tell:

- which lexical dataset is installed;
- the dataset date/identity;
- that dataset updates are manual/infrequent;
- that the current control does not silently download or replace data.

Do not implement full dataset download/import orchestration in this milestone unless a trivial already-supported safe path exists.

Avoid making this low-frequency maintenance feature visually dominant.

---

# J. Source Details / Provenance

Retain inspectability without turning the default learner view into a diagnostics page.

Review Source Details so that:

- the normal learner view remains simple;
- source sense identity, labels, glosses, provenance, and dataset identity can still be inspected;
- historical AI metadata remains historical only and is not surfaced as part of new deterministic entries unless explicitly reviewing legacy history;
- technical/debug information is secondary.

No deletion of historical provenance.
