# 1. Objective

M004.6.4 follows M004.6.3.

M004.6.3 established:

- bounded semantic-equivalence judgment is structurally viable;
- GPT-OSS produced some useful merge signal but also some questionable over-merging;
- Qwen3 8B was materially faster but, under the current binary contract, was too conservative and proposed no merges in the measured sample;
- deterministic conflict detection prevented unsafe transitive merges;
- naive one-call-per-pair all-pairs comparison does not scale to high-polysemy partitions;
- the next step should not automatically introduce embeddings;
- the immediate unanswered questions are:
  1. what exactly should count as one learner meaning;
  2. whether batching can reduce LLM-call cost substantially;
  3. whether a more conservative clustering policy improves semantic safety;
  4. whether a slightly richer but still bounded decision contract improves model calibration.

The objective of M004.6.4 is therefore:

> Define and benchmark a clearer learner-meaning consolidation policy, compare single-pair and batched bounded semantic judgments, evaluate conservative code-owned clustering, and determine whether the consolidation task can be made both semantically trustworthy and operationally practical without embeddings.

This milestone should answer:

1. Can we define a stable product-level policy for when two source senses should merge?
2. Does adding a bounded rationale improve GPT-OSS/Qwen calibration without giving the model topology authority?
3. Can many code-owned pair judgments be batched into one model call without degrading semantic quality?
4. Does anchor-based batching reduce call count enough to matter?
5. Does conservative complete-link or equivalent conflict-aware clustering outperform simple union-find transitivity?
6. Does GPT-OSS still provide better consolidation signal than Qwen under the refined contract?
7. Can Qwen become useful for consolidation when the semantic contract is clearer?
8. Is batching sufficient to make exact-word consolidation practical without embeddings?
9. If not, is there now measured justification for an embedding-screening milestone?

This milestone is NOT:

- a production grouping rewrite;
- a production core-ranking change;
- an embedding experiment;
- a runtime bake-off;
- a new-model evaluation;
- a full lexical benchmark;
- a frequency-ranking milestone;
- a learner-UI milestone.

# 7. Product-Level Consolidation Policy

Before live inference, encode a concise benchmark policy for:

> When should two source senses be represented by one learner-facing meaning container?

The policy should distinguish MERGE eligibility from semantic relatedness.

Preferred rule:

MERGE only when two senses express substantially the same learner concept and their difference is primarily:

- wording;
- example/context;
- ordinary application;
- near-paraphrase;
- minor contextual variation that does not teach the learner a genuinely different use.

KEEP SEPARATE when:

- one sense introduces a different concept;
- one is a broader/narrower specialized use that deserves separate learner treatment;
- one is domain-specific in a way that materially changes meaning;
- combining them would make the learner definition overbroad;
- register/material-label rules require separation;
- uncertainty remains.

Prefer false split over destructive false merge.

This is a product-policy benchmark, not a universal lexicographic truth claim.

# 10. Refined Bounded Decision Contract

Replace the previous pure:

- `same`
- `distinct`
- `uncertain`

benchmark contract with a decision plus diagnostic rationale.

Preferred structure:

{
  "decision": "merge",
  "reason": "paraphrase_or_duplicate"
}

Decision enum:

- `merge`
- `keep_separate`
- `uncertain`

Reason enum:

- `paraphrase_or_duplicate`
- `contextual_variant`
- `specialized_subsense`
- `broader_or_narrower`
- `related_but_distinct`
- `materially_different`
- `insufficient_evidence`

The exact names may be adjusted slightly for implementation clarity, but preserve the key architectural distinction:

- `decision` controls merge eligibility;
- `reason` is diagnostic semantic evidence.

Python must never infer a merge from `reason` alone.

Only:

`decision == merge`

may become positive merge evidence.

---

# 11. Decision Consistency Rules

Benchmark validation should reject or flag logically inconsistent combinations where practical.

Examples:

- `merge` + `materially_different` -> inconsistent;
- `merge` + `related_but_distinct` -> inconsistent;
- `keep_separate` + `paraphrase_or_duplicate` -> questionable/inconsistent unless explicitly justified;
- `uncertain` + any reason -> allowed where semantically defensible.

Do not create an overly complex ontology.

The goal is better diagnostics, not a new lexical taxonomy.

# 14. Experiment B — Batched Pair Judgment

# 17. Experiment C — Anchor-Based Judgment

- S004
- ...

- repeat.

The model does NOT create containers.

# 18. Anchor-Based Safety

Do not blindly accept anchor membership if it conflicts with known pair evidence.

Before finalizing a container, Python must ensure the proposed members are internally compatible under the chosen conservative policy.

If:

A merges with B
A merges with C
but B should remain separate from C

then do not silently produce {A,B,C}.

Flag conflict or split conservatively.

The anchor experiment is intended to reduce comparisons, not weaken semantic safety.

# 19. Conservative Clustering Policy

Replace or compare against simple transitive union behavior with a stricter code-owned clustering rule.

Preferred candidate:

**complete-link conservative merge**

A candidate sense may join an existing learner container only if all required known cross-container relationships support merging and none explicitly require separation.

At minimum:

- explicit `keep_separate` blocks merge;
- `uncertain` does not authorize merge;
- contradictory evidence is surfaced;
- no transitive merge may override explicit separation.

If another equivalently conservative deterministic algorithm is simpler and better supported by the existing benchmark structure, document it.

Do not use probabilistic topology.
