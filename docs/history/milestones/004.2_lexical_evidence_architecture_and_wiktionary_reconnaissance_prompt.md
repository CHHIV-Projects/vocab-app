# Vocab App M004.2 — Lexical Evidence Architecture and Wiktionary Reconnaissance

## 1. Purpose

M004.2 is a reconnaissance and architecture milestone only.

The goal is to define the long-term lexical evidence architecture for the Vocab application before implementing the richer Dictionary / Thesaurus / Etymology / Pronunciation path.

The intended direction is:

- Wiktionary-derived local data becomes the primary rich lexical evidence source.
- WordNet remains local and becomes a supplemental semantic/sense relationship source rather than the primary visible dictionary.
- gTTS remains the pronunciation-audio provider.
- PostgreSQL remains canonical application persistence.
- `gpt-oss:20b` may later synthesize and organize retrieved evidence, but AI output must remain derived rather than authoritative.
- Translation is now a separate product path and is explicitly out of scope for M004.2.

Do not implement the new lexical engine in this milestone.

## Product Owner controlling clarification

This clarification controls M004.2 where it refines or conflicts with earlier wording while preserving the original prompt as milestone history.

- M004.2 and the expected M004.3 implementation assume English lexical entries only. Preserve language, source-language, and borrowing metadata where supplied, but do not import all Wiktionary languages merely to filter them at runtime. Translation remains a separate product path.
- The M004.2 closeout must recommend one preferred Wiktionary-derived source approach after comparing raw Wiktionary XML extraction, Wiktextract-derived structured data, and Kaikki/Wiktextract pre-extracted English data on complexity, update workflow, field completeness, provenance, lookup suitability, storage, licensing, and operational simplicity.
- The closeout must provide realistic order-of-magnitude estimates for the recommended source: compressed download, extracted source, indexed/local-query size, host storage, Docker image impact, RAM, and import/index/update duration. The lexical dataset should not be copied into the normal application image unless reconnaissance demonstrates a strong reason.
- PostgreSQL remains user/application state: saved vocabulary, scores/history, accepted entry versions, and synthesis/provenance metadata. A separate replaceable/versioned lexical evidence store must hold Wiktionary-derived and appropriate WordNet/OEWN reference evidence. The closeout must compare PostgreSQL, SQLite/FTS, structured JSON/JSONL plus index, and any other bounded local index it recommends.
- Evidence identity is a first-class requirement. Recommend stable identities containing source type, source dataset/version, importer/schema version, language, lexical entry identity, sense identity, and field/relation identity. Do not use line numbers or import order. Previously accepted entries must retain the evidence version used even if later imports change or remove upstream entries.
- Wiktionary senses and WordNet synsets are parallel evidence, not assumed equivalents. Any later cross-source alignment must be explicit and marked evidence-backed, heuristic, or unresolved. Do not require automatic alignment in M004.3 unless this reconnaissance demonstrates it is bounded and reliable.
- Classify lexical fields as reliably structured, available but variable, or highly irregular/optional. Missing evidence remains missing; GPT-OSS must never fill absent canonical fields from model memory.
- The future GPT-OSS contract must distinguish factual claims from presentation text. Each factual item requires claim type, supporting evidence IDs, source versions, model, prompt version, evidence-set identity/hash, and validation status. Unsupported factual output must be rejected or omitted; AI confidence is not evidence.
- Saved-entry stability is a first-class later acceptance requirement: source evidence version -> derived synthesis version -> accepted entry version. Updating source data, WordNet, GPT-OSS, or prompts must not silently alter an accepted entry. Refresh must be explicit and create a new candidate/derived version for review.
- Licensing and attribution are required M004.2 deliverables. Document upstream Wiktionary licensing, extraction/distribution licensing, local-storage and derivative-data implications, attribution requirements, and whether Vocab needs UI, About/help, or both attribution surfaces.
- Translation remains separate and out of scope. Do not repair GoogleTranslator, adopt another translation service, or evaluate local-AI translation in M004.2.

The closeout must give concrete recommendations for:

1. preferred Wiktionary-derived source;
2. licensing and attribution;
3. approximate storage/update/resource cost;
4. physical lexical evidence store/index;
5. reliable deterministic fields;
6. stable/versioned evidence identity;
7. WordNet's supplemental role without false sense alignment;
8. GPT-OSS claim/synthesis boundary;
9. deterministic validation rules;
10. accepted-entry versioning and no-silent-regeneration behavior.

No production implementation is authorized in M004.2. Do not Stage, Commit, or Push.

## 2. Product context

The current M004.1 implementation is intentionally accepted as a transitional checkpoint.

It established useful boundaries and removed obsolete dependencies, but the current WordNet-first-definition behavior is not considered the final dictionary architecture.

The Product Owner observed that:

- WordNet definitions are often too sparse for the desired learner experience.
- selecting only the first WordNet synset suppresses important common senses;
- Wiktionary appears better suited to rich dictionary information;
- gTTS pronunciation audio is satisfactory and should remain because its consistent voice is desirable;
- local AI appears most promising as a bounded synthesis/aggregation layer over discrete evidence, not as the original source of lexical facts;
- AI can still omit, combine, distort, or invent information even when performing synthesis, so deterministic evidence and validation must remain authoritative.

## 3. Controlling architecture principle

The intended hierarchy is:

Source evidence
    ->
deterministic normalization
    ->
optional AI synthesis
    ->
deterministic validation
    ->
accepted/versioned presentation
    ->
PostgreSQL application state

AI must never become the canonical lexical database.

No layer should certify itself.

Original source evidence must remain recoverable independently of any AI-generated representation.

## 4. Reconnaissance questions

Perform bounded reconnaissance sufficient to answer the following.

### 4.1 Wiktionary source strategy

Determine the best practical way for this self-hosted application to consume English Wiktionary data locally.

Evaluate at least the realistic approaches relevant to this project, such as:

- raw Wiktionary dump parsing;
- Wiktextract-derived data;
- Kaikki or equivalent pre-extracted structured data;
- another clearly superior open/local approach if evidenced.

For each viable option identify:

- source and update mechanism;
- data format;
- approximate operational complexity;
- approximate storage footprint or order of magnitude where reasonably discoverable;
- whether incremental updates are practical or whether periodic replacement is simpler;
- licensing/attribution implications relevant to storing and displaying derived lexical data;
- whether the dataset can remain fully local at runtime;
- whether external network access is required during normal word lookup.

Do not download or import a large dataset in M004.2 unless a very small sample is necessary for reconnaissance.

### 4.2 Lexical fields available

Determine which desired fields can be obtained reliably from the preferred Wiktionary-derived source.

At minimum investigate:

- word / lemma;
- part of speech;
- multiple senses / definitions;
- sense ordering;
- usage labels;
- examples;
- inflected or derived forms;
- pronunciation / IPA;
- etymology/history;
- synonyms;
- antonyms;
- related terms;
- source language / borrowing history where available.

Identify which fields are consistently structured versus irregular or sparsely populated.

Do not assume every Wiktionary field is equally reliable or easy to extract.

### 4.3 WordNet role

Review the current Vocab WordNet usage and define its intended role after Wiktionary becomes the rich lexical source.

The expected direction is:

WordNet:

- semantic senses / synsets;
- semantic relationships;
- sense-aware synonym relationships;
- supplemental concept structure.

Wiktionary:

- learner-facing definitions;
- multiple senses;
- forms;
- etymology;
- pronunciation metadata;
- broader dictionary-style information.

Determine whether current NLTK WordNet remains sufficient or whether Open English WordNet should be considered later.

Do not replace the WordNet implementation during M004.2.

### 4.4 Canonical evidence schema

Propose a normalized lexical evidence model that can preserve source facts without AI modification.

The schema should support multiple sources and multiple senses.

At minimum consider entities conceptually equivalent to:

LexicalEntry

- normalized word / lemma
- language
- source
- source version
- retrieval/import version

Sense

- source-specific sense identifier
- part of speech
- gloss/definition
- usage labels
- examples
- sense ordering
- source provenance

Form

- form
- grammatical relationship
- source provenance

PronunciationEvidence

- IPA or other written pronunciation
- dialect/region where supplied
- source provenance

EtymologyEvidence

- source text or normalized evidence
- source provenance

SemanticRelation

- synonym
- antonym
- hypernym
- hyponym
- related term
- WordNet synset where relevant
- source provenance

The exact physical schema is not locked.

Recommend whether this evidence should live:

- directly in PostgreSQL;
- in a separate local lexical datastore/index;
- partly in source files with an index;
- or another bounded architecture.

Explain the tradeoffs.

### 4.5 Evidence identity and provenance

Every fact later exposed to AI should be traceable to deterministic source evidence.

Recommend an evidence identity model such as:

WIK:<entry>/<sense>/<field>
WN:<synset>/<relation>

or another stable equivalent.

The design must make it possible for later AI output to reference specific evidence IDs.

Do not rely on free-form source descriptions alone.

### 4.6 AI synthesis boundary

Define the future boundary for `gpt-oss:20b`.

The intended role is:

- organize multiple senses;
- identify common learner-relevant meanings;
- group related synonyms by sense;
- rewrite supported definitions into clear learner-friendly wording;
- summarize supported etymology;
- organize forms and usage;
- possibly generate concise section labels or explanations.

The model must not be permitted to originate unsupported lexical facts.

Propose the structured JSON contract that a later milestone should require from the model.

At minimum consider:

- word;
- parts of speech;
- selected/common senses;
- learner-friendly definition;
- source evidence IDs per claim;
- synonym groups;
- forms;
- etymology summary;
- usage notes;
- validation metadata.

AI output should be treated as derived data.

### 4.7 Deterministic validation

Define what ordinary code can verify before accepting AI synthesis.

At minimum consider checks for:

- valid JSON/schema;
- every referenced evidence ID exists;
- no definition without supporting evidence;
- no unsupported part of speech;
- no unsupported synonym;
- no unsupported etymology;
- no unknown source IDs;
- no malformed source mapping;
- required common senses not completely omitted;
- bounded output size;
- model/prompt/evidence version recorded.

Differentiate:

1. checks that can be deterministically enforced;
2. quality judgments that cannot be proven mechanically.

Do not treat model confidence as validation.

An optional second AI critic may later be useful for quality review, but it must not be considered an authoritative safety gate.

## 5. Stable saved-entry behavior

The future system must prevent local AI from silently rewriting accepted vocabulary entries.

Define a versioned model with three conceptually distinct layers:

1. Canonical source evidence
2. AI-derived synthesis
3. Accepted saved vocabulary entry

Once a user saves/accepts a word:

- reopening the word must not automatically regenerate it;
- a newer model, prompt, Wiktionary import, or WordNet version must not silently alter the saved entry;
- regeneration must be explicit;
- refreshed synthesis should create a new derived version or candidate rather than destructively replacing the prior accepted result;
- provenance should record which evidence version, model, and prompt produced each synthesis.

Recommend the minimum PostgreSQL changes or conceptual tables required to support this later.

Do not implement those tables in M004.2.

## 6. Pronunciation architecture

Preserve the following distinction:

Wiktionary-derived evidence:

- IPA;
- dialect/region metadata where available;
- written pronunciation evidence.

gTTS:

- actual audible pronunciation used by the application.

Do not replace gTTS in this milestone.

Do not use local AI as the pronunciation authority.

Identify any implications of using lexical IPA evidence alongside a consistent gTTS voice.

## 7. Desired future lookup flow

Evaluate and refine this target flow:

User enters word
    |
    v

    |
    +-- Wiktionary-derived evidence

    |

    |

    |

    +-- gTTS audio
    |

## 12. Stop / escalation protocol

Stop and report before broadening scope if reconnaissance reveals any of the following:

- the preferred Wiktionary-derived source has licensing terms incompatible with the intended application;
- the local dataset size or runtime requirements are materially larger than expected;
- reliable extraction of definitions/senses/etymology requires a materially different architecture;
- source evidence cannot be given stable enough identifiers for provenance;
- WordNet/Wiktionary sense alignment would require a large research problem rather than a bounded supplemental mapping;
- the proposed versioned evidence/synthesis model conflicts materially with the existing PostgreSQL architecture;
- the repository state is not safe for bounded reconnaissance.

Do not silently substitute another architecture or begin implementation.

Return the completed M004.2 closeout for Product Owner/architect review.

Do not Stage or Commit.
