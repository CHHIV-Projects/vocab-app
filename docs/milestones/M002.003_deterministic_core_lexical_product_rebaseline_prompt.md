# A. Architecture Rebaseline

Update the application architecture so the active product no longer depends on generative AI.

The core source of lexical truth is the local lexical dataset, primarily Wiktionary/Wiktextract-derived evidence.

The source meaning boundary is:

> **One canonical source sense becomes one learner meaning by default.**

A word may therefore show multiple meanings because it may have multiple source senses.

Do NOT semantically merge two distinct source senses merely because their glosses appear similar.

Allowed deterministic organization includes:

- grouping under part of speech;
- preserving source order;
- grouping under explicit source etymology boundaries where supported;
- formatting multiple gloss components that already belong to one canonical source sense;
- recognizing explicit source relationships such as form-of / plural-of / alternative-form relationships;
- suppressing purely duplicate presentation metadata where identity/evidence remain preserved;
- exact duplicate handling only where equivalence is deterministically provable from source records and does not destroy source provenance.

Do NOT recreate semantic consolidation through heuristics, embeddings, fuzzy similarity, or hidden LLM/model calls.

# B. Core vs. Additional Meanings

The learner UI should retain the existing Product Owner preference:

- show approximately **3–5 Core meanings** by default when enough meanings exist;
- provide **Expand all meanings** for the remainder;
- archaic/obsolete meanings may still appear when appropriate;
- source senses remain preserved even when placed in Additional.

However, the deterministic selection policy for Core vs. Additional must be evidence-based.

Before changing the current ranking/selection policy:

1. inspect what reliable deterministic fields are available in the lexical dataset and existing code, including:
   - source order;
   - POS;
   - labels;
   - explicit usage/frequency-like information if genuinely present;
   - WordNet/source support if already available;
   - explicit source relationships;
2. distinguish actual source evidence from inferred popularity;
3. propose the smallest deterministic Core-selection policy that can be defended;
4. if there is no clearly safe current policy beyond source order / simple label handling, STOP and raise a bounded Repo Control question with the recommendation rather than inventing a ranking algorithm.

No AI ranking.

# C. Meaning Presentation

For each displayed learner meaning:

- preserve canonical source-sense identity internally;
- show a concise, readable source-derived definition;
- do not invent or paraphrase beyond what deterministic source formatting safely supports;
- preserve material source labels where relevant;
- keep meanings grouped clearly by POS;
- retain source provenance/details in an expandable secondary surface rather than cluttering the default learner view.

Where one canonical sense contains multiple gloss components through source hierarchy/context, present them as one learner meaning when they are components of that same source sense, not as separate invented meanings.

Do not flatten different source senses into one definition.

# D. Synonyms

Product Owner decision:

> **Synonyms are per sense.**

Implement or complete sense-bound synonym presentation using source evidence.

Requirements:

- synonyms must attach to the exact canonical sense they are evidenced against;
- do not present one undifferentiated word-level synonym pool when linkage is available;
- do not infer synonym relationships with AI;
- if source synonym linkage is absent/ambiguous, prefer omission or clearly source-level presentation rather than invented linkage;
- preserve provenance sufficient to inspect where the synonym came from.

# E. Etymology

Use **source-derived etymology**.

Requirements:

- no generative summarization;
- preserve source wording/structure as faithfully as practical;
- format for readability;
- detailed/long etymology may be expandable;
- preserve etymology identity/source boundaries when multiple etymologies exist;
- do not silently combine unrelated etymology sections.

If current evidence extraction cannot safely produce a clean learner presentation, preserve the source-derived text and report the limitation rather than fabricating a summary.

# G. Save / Versioning

Saved words are **static and immutable**.

Requirements:

- reopening a saved word returns the saved accepted version by default;
- newer lexical data must never silently rewrite or relink that saved version;
- source evidence/version identity remains attached to the saved version;
- prior accepted history remains preserved;
- no automatic refresh of saved entries.

The current immutable versioning architecture should be retained where compatible.

---

# H. Lexical Dataset Update / Refresh

The Product Owner expects lexical dataset updates to be infrequent but wants the capability preserved.

The application should expose a simple user-visible dataset status/control.

Minimum product behavior:

- show the identity/date of the currently installed lexical dataset;
- provide a manual action/control for checking/importing or initiating the established dataset-update workflow, if that capability is already safely implementable;
- do not auto-update lexical data;
- for an unsaved lookup, use the current installed dataset;
- for a saved word, continue showing the static saved version;
- if a newer dataset is installed than the dataset behind a saved word, a **Refresh from newer dataset** action may become available;
- Refresh creates a new candidate from the newer lexical evidence;
- Refresh must not overwrite the saved version in place;
- acceptance of refreshed evidence creates a new immutable saved version and retains history.

If full dataset-download/import orchestration is not currently product-ready, implement/status the safe UI boundary and report the remaining operational gap rather than creating a fragile updater.
