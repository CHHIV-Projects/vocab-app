## 4. Provider Architecture

New module: `vocab_consolidation_provider.py`.

- `PairProvider` — a `Protocol` with one method, `judge_pair(request: PairProviderRequest) -> PairProviderResult`.
- `QwenPairProvider` — the real implementation. One `POST /api/chat` call judges exactly one pair; no batching, no streaming.
- `installed_model_digest()` / `confirm_installed_model_identity()` — preflight helpers that call `GET /api/tags` and raise `RuntimeError`
  (STOP) on any digest mismatch, rather than silently proceeding.
- The module does not import, call, or modify `OllamaProvider` or any `gpt-oss:20b` code path. It reuses only the shared,
  provider-agnostic parsing helpers `response_content()` and `strict_json_object()` from `vocab_synthesis.py`.

## 5. Pair Request Contract

`build_pair_prompt(partition, pair)` builds a deterministic, canonical-JSON prompt using **only fields already exposed by M004.6.9
domain evidence members** (no new evidence extraction), per the user's confirmed design decision:

```text
{
  "task": "Return exactly one JSON object matching the required schema.",
  "learner_consolidation_policy": "<the exact accepted M004.6.4 policy string, verbatim>",
  "word": partition.normalized_lemma,
  "part_of_speech": partition.pos,
  "material_partition": [...],
  "sense_a": {"source_sense_id", "definitions", "labels", "examples", "relations"},
  "sense_b": {"source_sense_id", "definitions", "labels", "examples", "relations"}
}
```

The policy string reused verbatim (confirmed with the user, sourced from
`tools/benchmarks/manifests/m004.6.4_policy_batched_reference.json`):

> "Merge only near-paraphrase, duplicate, or contextual-application variants. Keep specialized, broader/narrower, related-but-distinct,
> materially different, and uncertain senses separate. Prefer false splits."

`build_pair_request()` produces a `PairProviderRequest` (pair, partition, prompt, schema, model, semantic_options) that is fully
data-driven and independently constructible for tests without any network access.

## 6. Output Schema

`pair_decision_schema()` is the exact accepted single-pair M004.6.4 decision/reason JSON schema (adapted from
`tools/benchmarks/m0046_policy_batched_benchmark.py`'s `decision_schema()`), constrained to `additionalProperties: false` with:

- `decision`: enum `["merge", "keep_separate", "uncertain"]`;
- `reason`: enum `["paraphrase_or_duplicate", "contextual_variant", "specialized_subsense", "broader_or_narrower",
  "related_but_distinct", "materially_different", "insufficient_evidence"]`.

`QwenPairProvider.judge_pair()` never trusts the schema constraint alone: after parsing, it also calls
`vocab_consolidation.validate_decision_reason()` (the same M004.6.9 domain validator used by persistence), which additionally rejects
the contract's known-incompatible decision/reason combinations (e.g. `merge` + `specialized_subsense`). **Application-side validation
remains authoritative**, not the model's structured-output guarantee — this was directly exercised live (Section 18): Qwen produced
exactly this incompatible combination once, and it was correctly rejected as `retryable_failure`/`schema_invalid`, not silently
accepted.

## 7. Semantic Options

`QWEN_SEMANTIC_OPTIONS`:

```python
{"think": False, "temperature": 0, "seed": 5100, "num_predict": 256, "num_ctx": 16384}
```

- `think: False` is a **boolean** (matching the value already validated for Qwen in M004.6.1 benchmarks — unlike GPT-OSS's string
  `"low"`), and is sent verbatim as the top-level Ollama `think` field.
- `temperature: 0`, deterministic single-pair judgment, no majority voting.
- `seed: 5100` is a fixed, documented default: the M004.6.4 benchmark used three seeds (`5100, 5101, 5102`) for majority voting, with
  no single canonical "production seed" previously established. `5100` (the first of that accepted sequence) was selected as the
  single production seed and is recorded here explicitly for review; it is easily overridden by callers via the `semantic_options`
  parameter.
- `num_predict: 256`, `num_ctx: 16384` follow the M004.6.1 `MODEL_POLICIES` convention for `qwen3:8b`.
- Model identity (`{"name": "qwen3:8b", "digest": "<confirmed digest>"}`) and the full semantic options mapping both flow directly
  into `pair_judgment_identity()`/`consolidation_identity()`, so any option or seed change produces a materially different judgment
  identity rather than silently reusing prior results.

## 8. Failure Classification

`QwenPairProvider.judge_pair()` returns a `PairProviderResult` with `status` in `{"provider_success", "retryable_failure",
"terminal_failure"}`. `uncertain` is always classified as `provider_success` — it is never a failure fallback.

| Condition | Status | Classification |
|---|---|---|
| Transport timeout | retryable | `timeout` |
| Transport/connection error | retryable | `transport_failure` |
| HTTP 5xx | retryable | `provider_server_error` |
| Non-JSON HTTP body | retryable | `malformed_response` |
| `done_reason == "length"` (truncated) | retryable | `truncated_length` |
| Missing/non-string message content | retryable | `provider_response_shape` |
| Empty content | retryable | `empty_response` |
| Content not exactly one JSON object | retryable | `malformed_json` |
| Unexpected JSON keys | retryable | `schema_invalid` |
| Invalid/incompatible decision-reason (domain validator) | retryable | `schema_invalid` |
| HTTP 404 (model unavailable) | terminal | `model_unavailable` |
| HTTP 4xx (other, e.g. malformed request) | terminal | `provider_request_error` |

19 offline tests (`tests/test_vocab_consolidation_provider.py`) exercise every row above using mocked `requests.post`/`requests.get`
calls, with no network access.

## 9. Retry Policy

- `MAX_PAIR_ATTEMPTS = 3` (orchestrator default, overridable via `max_attempts`), matching the prompt's suggested default bound.
- A retry re-submits the **identical** `pair_judgment_identity` (same pair, evidence, partition, contract, model, semantic options) —
  retrying never changes semantic identity, only `attempt_count` and lease bookkeeping.
- `claim_pair()` increments `attempt_count` on every claim (existing M004.6.10 behavior, unchanged).
- After a retryable failure, if `attempt_count >= max_attempts`, the orchestrator escalates the pair to `failed_terminal` with
  classification `retry_exhausted`, using the existing `record_pair_failure()` transition (`running -> failed_terminal`), rather than
  leaving it retryable forever.
- An expired `running` lease (crash recovery) is first demoted to `failed_retryable` (classification `lease_expired`) via
  `record_pair_failure()`, reusing the existing M004.6.10 transition table, before being claimed again. This does not consume an
  extra attempt; the original attempt was already counted when the expired lease was first acquired.

## 10. Persistence Integration

The orchestrator (`vocab_consolidation_orchestrator.run_partition_consolidation`) performs no persistence logic itself; it only
sequences the existing M004.6.10 primitives:

1. `create_or_get_job(...)` — idempotent job creation/lookup by `consolidation_identity`.
2. If `job["status"] == "topology_validated"`: return immediately via `load_validated_containers()`, **zero provider calls**.
3. `initialize_pairs(job_id, partition)` — idempotent, `ON CONFLICT DO NOTHING`.
4. If `partition.expected_pair_count == 0`: call `finalize_topology()` directly, **zero provider calls**.
5. `list_resumable_pairs(job_id)` — already deterministically ordered by `logical_pair_id`; optionally bounded by `max_pairs`.
6. For each resumable row: reclaim expired leases, check retry exhaustion, `claim_pair()`, call the provider, then
   `store_validated_judgment()` (success) or `record_pair_failure()` (retryable/terminal).
7. `job_progress(job_id)` determines whether to `finalize_topology()` (exact coverage, zero failures) or return an `incomplete` /
   `blocked_terminal_failure` result.

`finalize_topology()` itself (unchanged M004.6.10 code) validates durable coverage via `assemble_complete_link` /
`validate_pair_coverage` before publishing a topology; the orchestrator never bypasses or duplicates that check.


## 14. Terminal Failure Behavior

`test_terminal_failure_blocks_topology_finalization`: a pair receiving a `terminal_failure` result is persisted as `failed_terminal`
and the job returns `blocked_terminal_failure` with `topology_identity is None`. A subsequent orchestrator invocation (fresh provider,
zero resumable pairs for the terminal row) still returns `blocked_terminal_failure` — a terminal failure permanently blocks topology
finalization for that job; it is never silently bypassed. `test_retry_exhaustion_escalates_to_terminal_after_max_attempts` confirms
the same blocking behavior when retries are exhausted rather than provider-reported terminal.

This live result is treated as a valuable, expected exercise of the safety mechanisms in Sections 6, 8, 9, and 14 (schema-adjacent
