## 3. Failure Being Addressed

Under the M004.6.11/M004.6.12-era contract
(`pair-judgment-v1-exhaustive-qwen`), Qwen was structurally permitted to
return internally inconsistent decision/reason combinations — most
prominently `merge` paired with `specialized_subsense` — which the
application layer correctly rejected as `schema_invalid`/retryable, but which
recurred deterministically on retry for specific real word/sense pairs. This
previously caused:

- `heron` (name partition) to fail with `schema_invalid` and require manual
  intervention.
- `gecko` (noun partition) to fail 2 of 3 real pairs as `failed_terminal`
  after exhausting all 3 retry attempts each, leaving the word's overall
  status `"blocked"` rather than `"complete"`.

The root cause was that the v1 contract only blocked 4 of the 21 possible
decision×reason combinations (a `merge`-only blocklist), leaving 10 other
invalid combinations (e.g. `keep_separate`/`insufficient_evidence`,
`uncertain`/`materially_different`) unaddressed at both the schema and prompt
level, and relying entirely on retry-and-hope rather than structurally
preventing the invalid output.

## 4. Current (v1) Contract — For Reference

`PAIR_JUDGMENT_CONTRACT_V1 = "pair-judgment-v1-exhaustive-qwen"`.
Validation was a narrow blocklist,
`_PAIR_JUDGMENT_CONTRACT_V1_INCONSISTENT_DECISIONS` (renamed from
`INCONSISTENT_DECISIONS`, kept byte-identical): only
`("merge", "specialized_subsense")`, `("merge", "broader_or_narrower")`,
`("merge", "related_but_distinct")`, `("merge", "materially_different")` were
rejected. All other 17 combinations — including semantically nonsensical
ones such as `("uncertain", "materially_different")` — were previously
accepted.

## 5. Root Cause Characterization

The v1 schema (`pair_decision_schema()` in `vocab_consolidation_provider.py`)
was a flat object with two independent enums (`decision`, `reason`), with no
structural coupling between them. The prompt policy text
(`LEARNER_CONSOLIDATION_POLICY`) described the reasons narratively but did
not explicitly state the compatibility rule. This let `qwen3:8b` freely
combine an accurate `reason` classification (e.g. `specialized_subsense`, a
correct semantic read of the sense pair) with an incorrect `decision`
(`merge`), because nothing in the schema or prompt prevented that
combination from being structurally representable.

## 6. v2 Contract

`PAIR_JUDGMENT_CONTRACT_V2 = "pair-judgment-v2-exhaustive-qwen"`, now the
default value of `PAIR_JUDGMENT_CONTRACT` used throughout the orchestrator,
persistence, and provider modules (all of which reference the shared
constant rather than a hardcoded string, so the version bump propagated
automatically).

Per the user's explicit direction (full 7-combination allowlist, not a
minimal blocklist patch), the new authoritative compatibility matrix is:

| Decision        | Permitted reasons                                                                      |
|-----------------|------------------------------------------------------------------------------------------|
| `merge`         | `paraphrase_or_duplicate`, `contextual_variant`                                          |
| `keep_separate` | `specialized_subsense`, `broader_or_narrower`, `related_but_distinct`, `materially_different` |
| `uncertain`     | `insufficient_evidence`                                                                   |

This is a **complete allowlist** across all 3 decisions × 7 reasons = 21
combinations: 7 accepted, 14 rejected. It is strictly stricter than v1 (which
only rejected 4 of 21).

## 7. Contract Versioning (Backward Compatibility)

`validate_decision_reason(decision, reason, *, contract_version=PAIR_JUDGMENT_CONTRACT)`
is now contract-version-aware:

- `contract_version == PAIR_JUDGMENT_CONTRACT_V1` → enforces the original
  narrow blocklist only (so historical v1 persisted `PairJudgment` rows,
  which are reconstructed as domain objects on load and re-run
  `__post_init__` validation, remain loadable exactly as originally
  validated).
- Any other (v2+) value → enforces the new strict `VALID_DECISION_REASONS`
  allowlist.

`PairJudgment.__post_init__` now calls
`validate_decision_reason(self.decision, self.reason, contract_version=self.contract_version)`
instead of the old 2-argument call, so the correct rule set is applied based
on the judgment's own recorded contract version — not the process-wide
default.

`pair_judgment_identity()` hashes `PAIR_JUDGMENT_CONTRACT` (the per-judgment
`contract_version` field) directly into the judgment identity, so v1 and v2
judgments/topologies for identical evidence are automatically distinct and
independently cacheable — no other identity-computation code required
modification.

## 9. Schema-Level (Structural) Validation

`pair_decision_schema()` in `vocab_consolidation_provider.py` was rewritten
from a flat schema with independent `decision`/`reason` enums to a `oneOf`
schema with three discriminated branches — one per decision — each pinning
`decision` to a `const` value and restricting `reason` to only that
decision's permitted reasons (`const` for the single-reason `uncertain`
branch, `enum` for the multi-reason `merge`/`keep_separate` branches). This
structurally prevents the JSON schema from ever representing an invalid
combination, independent of the application-side check.

This was verified as actually enforced by Ollama's structured-output support
(not just assumed): a live call against `qwen3:8b` using the new schema was
made and returned a schema-conformant response, confirming `oneOf`/`const`
constructs are honored by the local Ollama/qwen3:8b structured-output path
(Ollama `0.32.5`).

`tests/test_vocab_consolidation_provider.py::PairDecisionSchemaTests` was
rewritten to assert the new 3-branch `oneOf` shape and per-branch reason
restriction.

## 10. Application-Level (Authoritative) Validation

Per Section 19 of the controlling prompt, the schema-level structural
constraint is defense-in-depth only. `validate_decision_reason()` remains the
sole authority: any `PairJudgment` construction with a schema-invalid or
allowlist-invalid decision/reason combination raises `ValueError`
regardless of whether the underlying schema "should have" prevented it,
preserving the existing retry/failure-classification behavior in the
orchestrator (`schema_invalid` → `failed_retryable` → retry, then
`failed_terminal` after exhaustion).

`merge`. Reviewing each:

- `heron`, `lynx`: previously-known separate-worthy proper-name senses;
  correctly remained `keep_separate` under v2 (no regression toward an unsafe

  (`specialized_subsense` for the two anomalous pairs, `materially_different`

  not the *semantic outcome*, which is the intended, conservative result.
- `otter`, `puma`: fresh control samples, both correctly `keep_separate`.

No unsafe or surprising merge was produced in any live sample; the
conservative (false-split-tolerant, false-merge-averse) posture established
in earlier milestones is preserved under v2.

**No live "merge" decision was observed** despite 8 samples across `heron`,
`gecko` (×3), `lynx`, `otter`, `puma` (×2). This is assessed as a
characteristic of the corpus rather than a defect: Wiktionary/curated
dictionary senses are pre-edited to be distinct, so true paraphrase/duplicate
sense pairs are inherently uncommon among arbitrarily sampled real words.
Positive evidence that the v2 contract still correctly supports `merge` when
warranted comes from two independent, deterministic sources instead of an
additional live sample:

1. **Offline provider tests** (`tests/test_vocab_consolidation_provider.py`,

   accept and construct a `merge`/`paraphrase_or_duplicate` (or
   `contextual_variant`) judgment when the provider legitimately returns
   one — the code path is not accidentally blocking `merge`.
2. **The merge-eligible reason set is unchanged between v1 and v2**
   (`paraphrase_or_duplicate`, `contextual_variant`); the v2 prompt only adds
   constraining guidance about when `merge` is *not* appropriate, and does
   not alter or restrict the model's positive criteria for recognizing a
   genuine duplicate/paraphrase pair. Historical M004.6.4 benchmark evidence
