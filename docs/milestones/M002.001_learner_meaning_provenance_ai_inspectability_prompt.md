## 1. Objective

Make the learner-facing meaning presentation more inspectable without changing lexical authority or semantic policy.

The learner should be able to understand, at an appropriate product level:

- which displayed learner meanings are synthesized/organized presentation rather than source-authored truth;
- which authoritative source meaning(s) support each displayed learner meaning;
- how many source meanings support a learner meaning;
- which source evidence belongs to the exact candidate/version being viewed;
- whether the displayed result is an unsaved candidate, an accepted saved version, a Retry candidate, or a Refresh candidate;
- enough bounded model/provenance metadata to understand how the candidate was produced without exposing private model reasoning.

This milestone should build on the accepted M002.000 lifecycle baseline rather than reopen it.

## 8. Product Contract — Learner Meaning Provenance

The default learner view must remain concise. Provenance should be available progressively rather than turning every definition into a diagnostics screen.

Preferred product direction:

### Meaning-level cue
For each learner meaning, provide a compact expandable cue such as:

`Based on N source meaning(s) ▸`

Equivalent wording is acceptable if it is clearer in the existing UI.

The count must be deterministic from the evidence references actually supporting that learner meaning. Never infer a count from prose similarity.

### Expanded meaning provenance
When expanded, show the authoritative source meaning(s) supporting that learner meaning, using existing stored evidence. Prefer learner-readable fields such as:
- source definition/gloss;
- source labels where material;
- relevant source sense identity/locator in a secondary/detail position;
- source name/dataset where useful.

Do not duplicate large raw evidence payloads unnecessarily.

### Candidate/version provenance
The existing Source Details / Advanced Details areas may be extended or reorganized narrowly to make clear:
- candidate origin: Search, Retry, or Refresh;
- whether this is an unsaved candidate or saved accepted version;
- accepted version number where applicable;
- source dataset/evidence identity;
- evidence hash in advanced detail, not primary learner copy;
- synthesis model identity;
- validator/policy/schema identities where already preserved and useful for technical inspection.

Use human-readable labels. Raw hashes/IDs belong in Advanced/technical details rather than the primary learner surface.

### AI boundary language
The UI should accurately communicate that:
- Wiktionary/Wiktextract evidence is source authority;
- GPT-OSS may organize/group/paraphrase learner-facing meanings;
- deterministic code validates evidence references and structural completeness before a candidate is eligible to save.

Do not imply that the LLM independently verified lexical truth.

## 9. Private Reasoning Boundary

“AI inspectability” does **not** mean exposing chain-of-thought, hidden reasoning, `message.thinking`, internal scratchpads, or other private model reasoning.

Do not display or persist private reasoning for the learner.

Existing bounded diagnostic retention may remain an engineering diagnostic mechanism under current architecture, but this milestone’s learner-facing inspectability should be based on:
- source evidence;
- deterministic mappings;
- model/config identity;
- candidate origin;
- validation/provenance metadata;
- accepted-version history.

## 10. Saved-Version / Retry / Refresh Correctness

Provenance shown for an accepted saved version must come from that version’s stored candidate/evidence snapshots, not silently from today’s current lexical dataset.

Retry:
- continues to use the exact stored evidence snapshot;
- provenance shown for the pending Retry candidate must therefore reflect that stored snapshot;
- if saved, the new accepted version retains its exact evidence/candidate provenance.

Refresh:
- continues to be available only when current evidence identity differs;
- a pending Refresh candidate may show changed/current evidence provenance;
- do not blur it with the prior accepted version’s stored evidence;
- if saved, the new version retains the new exact snapshot.

Search:
- provenance reflects the evidence used to construct that unsaved candidate.

Do not change the accepted-versus-pending state model established in M002.000 unless a demonstrable M002.001 defect requires a narrow correction.
